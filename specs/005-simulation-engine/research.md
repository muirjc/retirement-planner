# Phase 0 Research: Simulation Engine

No items in Technical Context were left as `NEEDS CLARIFICATION` — language, testing, and platform follow directly from `001`–`004`'s established choices. The research below resolves the feature-specific design questions this spec's Assumptions and Edge Cases raised — this is the first feature to generate genuine randomness, run at Monte-Carlo path volume, and add a comparison axis `004` didn't build.

## 1. How does `004`'s single-scalar `return_assumption` become path-varying without breaking `004`?

**Decision**: Introduce a small structural protocol, `ReturnSchedule`, with one method: `return_for_plan_year(self, plan_year: int) -> float`. `comparison.models.DeterministicReturnAssumption` gains this method (returning `self.annual_real_return` unconditionally, ignoring `plan_year`) — its existing `annual_real_return` field is untouched. This feature's own `ReturnPath` (research.md §2) implements the same method by indexing into its per-year list. `comparison.projection.run_plan_projection()`'s one growth-factor line changes from `return_assumption.annual_real_return` to `return_assumption.return_for_plan_year(plan_year)`; its parameter's type hint widens from `DeterministicReturnAssumption` to `ReturnSchedule`. No other line in `run_plan_projection()`, and no line in any of `004`'s three `compare_*()` functions, changes.

**Rationale**: `004`'s own contract (contracts/comparison-api.md § Consumption expectations) explicitly names this as the intended seam: "`run_plan_projection()` is the single entry point a future Simulation Engine feature will call once per Monte Carlo path per candidate, substituting a randomly-drawn per-year return sequence for `return_assumption` — this contract's per-year steps... do not change shape when that happens, only where `return_assumption` comes from." A protocol method is the minimal change that honors that promise: every existing `004` test constructing a `DeterministicReturnAssumption` and reading `.annual_real_return` directly (quickstart.md §1) keeps working unmodified, while `run_plan_projection()` becomes agnostic to which concrete return source it's given (Principle IV).

**Alternatives considered**: Duplicating `run_plan_projection()`'s entire per-year loop inside this feature's own package, parameterized differently — rejected; it would fork the RMD → mechanics → tax → tax-funding-withdrawal → growth sequence into two copies that could silently drift, exactly the risk `004`'s contract note was written to prevent. Making `ReturnPath` itself masquerade as a `DeterministicReturnAssumption` subclass with a year-dependent `annual_real_return` *property* instead of a same-named method — rejected; a property that silently returns a different value depending on hidden internal cursor state (which plan year was "current") is much harder to reason about and impossible to call from a stateless, parallelized per-path worker than an explicit `plan_year` argument.

## 2. How is the paired-draw guarantee enforced structurally, not just asserted?

**Decision**: A single function, `generate_return_paths(market_assumptions, path_count, horizon_years, seed) -> list[ReturnPath]`, produces the complete path set once, before any candidate is run. Every `run_simulation()` and `compare_*()` call takes that same `list[ReturnPath]` object as an argument and passes it through, path-for-path, unmodified, to every candidate it runs — `path_results[i]` for every candidate is always the projection of `return_paths[i]`. The four comparison functions (`compare_states`, `compare_roth_conversion_strategies`, `compare_withdrawal_sequencing_strategies`, `compare_claiming_age_grid`) each vary exactly one input across their candidate list while forcing every other input — including `return_paths` — identical across every call, mirroring `004`'s `replace()`-based pattern (`004`'s `compare.py`).

**Rationale**: The constitution names "identical random draws reused across scenarios" as the standard; the only way to guarantee that mechanically (not just by convention) is for every candidate to consume the same in-memory sequence object rather than each deriving its own from the same seed — two independently-seeded generators are only guaranteed identical if nothing about their call order ever diverges between candidates, which is fragile to depend on as candidates grow more complex (e.g., a state comparison where each state's tax module makes a different number of internal calls). Pre-generating once and threading the same list through removes that fragility entirely.

**Rationale (state axis)**: `state` is a top-level `run_plan_projection()` argument, not a `StrategyConfiguration` field — `004`'s `StrategyConfiguration` never included it (data-model.md §4's `Household`/`state` are call-level, not per-candidate, in `004`). Rather than adding an optional `state` field to `StrategyConfiguration` (which would let every existing `004` comparison silently start varying state too, unless every call site remembered to force it fixed — the opposite of `004`'s own "candidate list forces every other field identical" discipline), this feature adds a fourth, parallel `compare_states()` function taking `states: list[str]` directly and holding one `StrategyConfiguration` fixed across all of them. This keeps `004`'s three existing comparison functions and their contracts completely untouched.

**Implementation note (added during `/speckit-implement`)**: The identical-object guarantee described above holds for the *input* `return_paths` list every candidate consumes (every candidate is handed the same list reference) and for every candidate's *values* (path-for-path equal `annual_returns`) regardless of dispatch. It does **not** extend to the *output* `PlanProjection.return_assumption` object's identity once `run_simulation()` dispatches path-level work through `ProcessPoolExecutor` (research.md §7): a worker-process round trip through pickling necessarily produces a deserialized copy, so `is` no longer holds for `path_results[i].return_assumption` above the parallel-dispatch threshold, even though `==` (dataclass value equality) still does. Callers that need an identity check should do so only below that threshold (serial dispatch); at Monte-Carlo scale, value equality is the correct and sufficient guarantee. `tests/unit/simulation/test_compare.py` exercises the identity form (small, serial path counts); `tests/integration/test_simulation_lifecycle.py` and quickstart.md §2 exercise the value-equality form (reference-scale, parallel path counts).

**Alternatives considered**: Re-seeding a fresh `random.Random(seed)` inside each candidate's own run — rejected, per the mechanical-guarantee argument above. Threading a raw `seed` integer through every function instead of a materialized `list[ReturnPath]` — rejected; it would force every consumer (including a future reporting feature) to re-derive the same paths to inspect them, and would make the "single-candidate comparison is still valid" edge case (FR-010, mirroring `004`'s FR-011) harder to distinguish from "comparison with no real pairing guarantee yet."

## 3. How are correlated equity/bond return draws generated without a numeric array library?

**Decision**: `generate_return_paths()` uses one `random.Random(seed)` instance, consumed in a fixed order: for each path index `0..path_count-1`, for each plan year in the horizon, draw two independent standard normal deviates via `Random.gauss(0.0, 1.0)`, then transform them into a correlated `(equity_return, bond_return)` pair using the closed-form Cholesky factorization of the 2×2 covariance matrix implied by `equity_return_std_real`, `bond_return_std_real`, and `correlation` (`001`'s `MarketAssumptions`):

```text
z1, z2 = gauss(0,1), gauss(0,1)
equity_return = equity_return_mean_real + equity_return_std_real * z1
bond_return   = bond_return_mean_real + bond_return_std_real * (correlation * z1 + sqrt(1 - correlation**2) * z2)
blended_return = equity_allocation * equity_return + bond_allocation * bond_return
```

Only `blended_return` is retained per year (one float), matching `004`'s Decision 6 that a single blended rate is applied to all three account types every year (`004`'s research.md §6) — there is no scenario input that would let this feature grow account types at different rates, so carrying separate equity/bond components past this point would be dead data.

**Rationale**: This is the textbook two-variable Cholesky decomposition, computable in closed form without a matrix library — exactly the shape `numpy.random.multivariate_normal` would produce for a 2×2 covariance matrix, but expressible in five lines of stdlib `random`/`math`. Consuming the RNG in a fixed, fully-specified order (path, then year, then `z1`-before-`z2`) is what makes Decision 1's reproducibility argument concrete: the sequence of `.gauss()` calls for a given seed is deterministic and independent of how many CPU workers later consume the resulting `ReturnPath` list (research.md §7).

**Alternatives considered**: Adding `numpy` for `numpy.random.default_rng(seed).multivariate_normal(...)` (what the source prototype actually does) — considered directly, addressed in research.md §6 rather than dismissed here, since it is the more consequential dependency decision. Ignoring `correlation` entirely and drawing equity/bond independently — rejected; `001`'s schema carries `correlation` specifically because the source document's reference profile uses a negative equity/bond correlation, and silently dropping it would be exactly the kind of unstated simplification Principle I forbids.

## 4. Where does the historical return series live, and how is a path built from it?

**Decision**: `simulation/historical_data.py` defines `HISTORICAL_RETURNS: SourcedFigure[tuple[float, float]]`, reusing `002`'s existing `SourcedFigure` type (`retirement_planner.tax.SourcedFigure`) with its `schedule` keyed by calendar year and each value a `(equity_real_return, bond_real_return)` pair, `citation` describing the intended composite series (a broad-coverage equity total-return index plus an aggregate bond index, spanning approximately 1926–present per spec.md's Assumptions), and `verified=False` until cross-checked against a primary source — the same `usage_for_year()` / `FigureUsage` mechanics `002`'s state modules already use. `generate_historical_bootstrap_paths(path_count, horizon_years, seed, block_length)` builds each path by repeatedly choosing a random starting year (via the same `random.Random(seed)` stream) such that `block_length` consecutive documented years exist in `HISTORICAL_RETURNS.schedule`, taking that contiguous block's blended returns (allocation-weighted the same way as research.md §3), concatenating blocks until the path reaches `horizon_years`, then truncating to exactly `horizon_years`. Every generated path's `figures_used` includes `HISTORICAL_RETURNS.usage_for_year()` for the specific years actually drawn into it.

**Rationale**: Reusing `SourcedFigure` rather than inventing a parallel citation type keeps exactly one auditability primitive in the codebase (Principle IV) and gets the "raise, never fall back or interpolate" discipline (`SourcedFigure.value_for_year()`) for free — a request naming a `block_length` or date range the series can't cover raises the same class of explicit error `002`'s `UnsupportedTaxYearError` does, rather than silently substituting a shorter block (FR-013, US3 Acceptance Scenario 4). The moving-block-bootstrap method (resampling contiguous historical blocks, not individual years) is what the source document asks for explicitly ("fat tails and real sequencing... matter") — resampling individual years independently would destroy exactly the historical sequencing the feature exists to capture.

**Alternatives considered**: Fetching a return series from a live data provider at run time — rejected outright by Principle V (Offline-First); the source document's own §4 non-functional requirement is explicit that any rate lookup is a separate, explicit refresh action, never a runtime dependency. Wraparound block sampling (allowing a block to wrap from the series' last year back to its first) — rejected as introducing an artificial, non-historical adjacency between economically unrelated years; a request whose parameters don't fit without wraparound is rejected instead (FR-013).

## 5. How is the survival-adjusted success metric computed, and where does the survival curve live?

**Decision**: A new type, `SurvivalCurve` (`person_name`, `probabilities_by_age: dict[int, float]`, `citation`, `last_verified`, `verified`), purpose-built rather than a reuse of `SourcedFigure` — `SourcedFigure.schedule` is keyed by *tax year*, while a survival curve is inherently keyed by *age*, and forcing age into a "tax year" key would either produce misleading `UnsupportedTaxYearError`-shaped errors for the wrong axis or require a confusing renaming of that mechanism's own vocabulary. `SurvivalCurve` carries the identical `citation`/`last_verified`/`verified` fields by convention and exposes `.usage() -> FigureUsage` so it plugs into the same `figures_used` propagation as every other sourced figure (FR-019). `simulation/survival_data.py` defines one `SurvivalCurve` per household-member role (`SURVIVAL_TABLE: dict[str, SurvivalCurve]`, e.g., keyed by a role like `"primary"`/`"spouse"` a caller maps its `HouseholdMember`s onto), sourced from a standard published period life table, `verified=False` pending confirmation. A path's outcome is scored survival-adjusted-successful unless: (a) its fixed-horizon `first_shortfall_plan_year` is not `None`, **and** (b) at that shortfall's plan year, at least one household member's translated age has `survival_probability >= 0.5` (i.e., that member is "presumed alive" — more likely surviving than not, per spec.md US5 Acceptance Scenario 3's "more likely deceased than alive" wording).

**Rationale**: This directly implements the spec's own acceptance criteria (US5 AS1–AS3) — a *threshold* determination per member at the shortfall year, not per-path stochastic death sampling. Stochastic death sampling (drawing an actual death year per member per path from the survival curve, then checking whether it precedes the shortfall) is a materially different and more complex model that the spec's acceptance scenarios don't describe or require (they describe a curve "placing" a member as alive or deceased, i.e., a probability compared against a fixed threshold) — building it now would be scope creep past what FR-017/FR-018 actually ask for, and the spec's own Assumptions section frames survival-adjustment as an additive, optional, deliberately modest first cut (the source document's own §3.5 wording is "consider optional...").

**Alternatives considered**: Stochastic per-path death-year sampling, jointly drawn alongside each path's return sequence — rejected for the scope-creep reason above; noted here as a natural, larger follow-on if a future feature wants genuine joint mortality/market risk rather than this feature's threshold approximation. Requiring one household-level combined survival curve instead of one per member — rejected; the spec's US5 explicitly frames failure as depending on *each* member's individual survival ("at least one household member's survival curve indicates them as still living"), which a single combined curve can't express.

## 6. Why does this feature stay stdlib-only rather than adopting `numpy` (which the source prototype uses)?

**Decision**: No new third-party runtime dependency. Correlated-normal generation uses the closed-form two-variable Cholesky transform (research.md §3); percentile aggregation uses `statistics.quantiles` (stdlib, available since Python 3.8); the performance risk this decision creates is addressed separately via parallelism (research.md §7), not via vectorization.

**Rationale**: `numpy` would meaningfully speed up only the return-draw generation step — a small fraction of this feature's total cost. The dominant cost is the per-plan-year mechanics/tax/withdrawal call chain this feature invokes once per path per year via `run_plan_projection()`, which is built entirely on `002`/`003`/`004`'s dataclass-and-float arithmetic, not numpy arrays; vectorizing return generation alone would not touch that bottleneck, and rewriting `002`–`004` to operate on numpy arrays instead of per-year dataclasses is far outside this feature's scope (and would violate this feature's own scope note against re-implementing RMD/withdrawal/conversion/tax mechanics). Continuing the "no new third-party dependency" precedent `002`–`004` established, for a dependency that wouldn't solve the actual bottleneck, is the more honest choice than adding it for a partial, misleading speedup.

**Alternatives considered**: Adopting `numpy` anyway, and additionally rewriting the per-year loop to operate on batched arrays across paths — rejected as a much larger, riskier rewrite of already-shipped and tested `002`–`004` code, undertaken inside a feature whose spec explicitly scopes it out ("does not perform RMD determination, withdrawal execution, or Roth conversion execution itself"). Using `numpy` only for return-path generation while leaving the mechanics loop untouched — rejected as adding a dependency for a part of the workload that isn't the actual performance risk (research.md §7 shows where the real risk is), when a stdlib closed-form solution already exists at equivalent cost.

## 7. How does this feature meet the Performance Budget (Constitution Principle VI) at genuine Monte-Carlo volume?

**Decision**: `monte_carlo.run_simulation()` and each `compare_*()` function dispatch path-level work through `concurrent.futures.ProcessPoolExecutor` once the requested path count exceeds a small threshold (exact threshold and chunk size determined empirically during implementation, not asserted here), submitting `run_plan_projection()` calls for pre-generated `ReturnPath`s across worker processes and collecting results back in path-index order. A dedicated benchmark test (`tests/integration/test_simulation_performance.py`, referenced in plan.md's Project Structure) asserts the reference-scale case (3,000–5,000 paths × up to 9 states) completes in well under a minute on CI/dev hardware, and this feature is not considered complete until that benchmark passes — not merely designed to pass.

**Rationale**: This is the first feature in the project to run the per-year mechanics/tax loop at thousands-of-paths-times-decades volume; `004`'s plan.md performance estimates (an already-conservative "well under 50ms" per plan year, "well under 2 seconds" per 35-year projection) were sized for single-digit-to-low-hundreds candidate counts, not Monte Carlo path counts — extrapolated naively to 5,000 paths × 9 states, that budget would be exceeded by orders of magnitude. Paths are embarrassingly parallel (each is a pure function of one `ReturnPath` plus the shared, read-only scenario/strategy inputs — no shared mutable state, no cross-path dependency), making process-level parallelism a natural fit without touching `002`–`004`'s internals at all. Pre-generating the full `ReturnPath` list before dispatch (research.md §2) is what keeps this parallelism reproducible (Principle II): workers only ever consume already-materialized, order-indexed data, so wall-clock scheduling nondeterminism across workers cannot change which returns produced which path's result.

**Implementation note (added during `/speckit-implement`)**: Dispatching work through `ProcessPoolExecutor` surfaced a real, narrow defect this feature's own testing needed to fix: `retirement_planner.tax.UnsupportedTaxYearError` (`002`) overrides `__init__` with a signature (`figure_name`, `requested_year`, `available_years`) that doesn't match the single formatted message `BaseException.__reduce__` would otherwise try to replay when reconstructing the exception in the parent process — an `UnsupportedTaxYearError` raised inside a worker therefore failed to unpickle, surfacing as an opaque `BrokenProcessPool` instead of the real, correctly-typed error a caller's code (and this feature's own contracts) already promise. Fixed with a minimal, additive `__reduce__` on that exception class (in `002`'s own `tax/models.py`) so it reconstructs from its actual constructor arguments — the same category of small, justified cross-feature touch `004` made to `003`'s `WITHDRAWAL_STRATEGIES` registry. No other exception type raised inside this feature's worker path (`ValueError`, `KeyError`) needed the same fix — both accept `__init__(*args)` compatible with `BaseException`'s default `__reduce__`.

**Alternatives considered**: Threading (`ThreadPoolExecutor`) instead of process-based parallelism — rejected; the per-path work here is CPU-bound Python (dataclass construction, float arithmetic, dict lookups), which the GIL prevents threads from speeding up meaningfully. Accepting the performance risk without a mitigation, deferring optimization to a future feature — rejected; Principle VI requires a regression to be "flagged and justified (or optimized) before being merged," and shipping a feature whose own stated purpose (SC-003) is explicitly a runtime budget without addressing the one place that budget is actually at risk would violate the principle's own text, not merely its spirit. Reducing the default reference-scale path count instead of parallelizing — rejected; the source document's own non-functional requirement and this feature's SC-003 both name 3,000–5,000 paths specifically, matching the existing prototype's proven scale, and silently shipping a smaller default would quietly regress the tool's stated capability rather than meet it.
