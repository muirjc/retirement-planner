# Phase 0 Research: Reporting & Aggregation

No items in Technical Context were left as `NEEDS CLARIFICATION` — language, dependencies, storage, testing, and platform follow directly from `001`–`005`'s established choices. The research below resolves the feature-specific design questions this spec's Assumptions and Edge Cases raised — this is the first feature to read `004`'s and `005`'s output types as pure input rather than producing new results of its own.

## 1. How does this feature compute a "deemed household member's age" without re-deriving `004`'s logic, and without `001`/`004`/`005`'s result types changing?

**Decision**: `summarize_run()`, `summarize_simulation_comparison()`, and `summarize_deterministic_comparison()` all take `household: Household` and `reference_tax_year: int` as explicit caller-supplied arguments — the exact same two pieces of context every existing `004`/`005` function already requires as arguments, never stored on or derivable from `PlanProjection`/`SimulationRun`/`ComparisonResult` themselves. Given a depleted path's `first_shortfall_plan_year`, the corresponding `tax_year` is read directly from that `PlanYearProjection.tax_year` (already stored per year — no separate `start_tax_year` needed), then translated to the deemed owner's age via two helpers this feature reuses from `004` rather than re-implementing: `deemed_rmd_owner(household)` and `member_age_in_tax_year(member, tax_year, reference_tax_year)`. Both already exist in `004`'s `comparison/projection.py` as private (`_`-prefixed) helpers (`_deemed_rmd_owner`, `_member_age_in_tax_year`) — this feature renames them to public (dropping the underscore) and adds them to `comparison/__init__.py`'s exports, a mechanical, behavior-preserving change.

**Rationale**: `004`'s own result types (`PlanProjection`, `PlanOutcome`) deliberately carry no `household`/`reference_tax_year` reference — every `004`/`005` function takes them as plain arguments instead (`run_plan_projection()`, `run_simulation()`, every `compare_*()`), and this feature's spec explicitly commits to not modifying `001`–`005`'s existing types (FR-014). Reusing `004`'s exact age-translation formula, rather than writing a second copy of `current_age + (tax_year - reference_tax_year)`, eliminates any risk of the two calculations silently drifting apart (Principle I) — a real risk given they'd otherwise be the same three-line formula maintained in two places. Renaming rather than duplicating is the smaller, more honest change: the logic is unchanged, only its visibility.

**Alternatives considered**: Adding `household`/`reference_tax_year` fields to `PlanProjection`/`SimulationRun` so they're self-contained — rejected; it would touch two already-shipped, already-tested result types for a convenience only this feature needs, and would let a `PlanProjection`'s stored household silently diverge from the one actually used to compute it (a manufactured second source of truth). Re-implementing the age-translation formula locally in `reporting` — rejected per the drift-risk reasoning above; a mechanical rename-and-export is strictly safer than a second implementation of the same three lines.

## 2. What does "not applicable" mean for a field that a deterministic `ComparisonResult` genuinely doesn't have (success rate, percentile bands)?

**Decision**: `SummaryStatistics.success_rate: float | None` and `SummaryStatistics.percentile_bands: list[PercentileBand] | None` are `None` when summarizing a deterministic `004` candidate (a single fixed-return path has no probability distribution to report a success *rate* over, and no percentile spread to report bands for — there is only one value). Every Monte Carlo (`005`) summary populates both fields. `SummaryStatistics.unverified_figure_names: list[str]` is never `Optional` — it is always a list, empty or not, since "zero unverified figures" and "not applicable" are genuinely different facts a reader must be able to tell apart (Edge Cases, Acceptance Scenario US4.2).

**Rationale**: Conflating "doesn't apply to this input type" with "happened to be zero/empty" would let a UI (a future `008` consumer) render a deterministic candidate's success rate as `0%` — actively misleading, since `0%` asserts "this configuration always fails," not "this metric doesn't exist for this input." `None` vs. a populated (possibly empty) collection is the same distinction Python's own type system already makes idiomatic, and it's the same discipline `SimulationRun.survival_adjusted_success_rate: float | None` in `005` already established for its own "not requested" case.

**Alternatives considered**: Raising an error when a deterministic input is summarized for a Monte-Carlo-shaped field — rejected; FR-006 explicitly requires deterministic comparisons to be summarizable at all, just with a smaller genuine field set, not an error. Reporting `0.0`/`[]` in place of `None` — rejected per the misleading-UI reasoning above.

## 3. What does `SummaryStatistics.ending_balance` mean across two structurally different inputs (one Monte Carlo distribution vs. one deterministic value)?

**Decision**: `ending_balance` is always populated (never `None`) as one headline number, computed differently per input type but comparable across both: for a Monte Carlo `SimulationRun`, it is the run's own `percentile_bands[-1].percentiles[0.50]` (the median final-year ending balance — no new computation, a direct read of `005`'s own already-computed 50th-percentile figure); for a deterministic `PlanProjection`, it is `outcome.ending_balance` directly (the only ending balance that exists for a single fixed path).

**Rationale**: FR-006 names "ending balance" as one of the fields a deterministic candidate genuinely has, alongside `percentile_bands`/`success_rate` (which it doesn't) — this decision gives every `SummaryStatistics` instance exactly one comparable "how much money is left" headline figure regardless of which engine produced it, so a reader (or a future `008` UI table) never has to branch on input type to answer "what's the bottom-line number here." Using the median (not the mean) for the Monte Carlo case matches the percentile-band convention `005` already established throughout its own output.

**Alternatives considered**: Reporting the mean ending balance for Monte Carlo inputs instead of the median — rejected; `005` doesn't compute a mean anywhere (only percentiles), and introducing one here would be new computation this feature's own scope note disclaims (FR-014). Leaving `ending_balance` `None` for one input type or the other — rejected; unlike success rate/percentile bands, every input type genuinely has *some* answer to "what's the ending balance," so `None` would misrepresent an available fact as absent.

## 4. How does `summarize_simulation_comparison()` relate to `summarize_run()`, and how does `summarize_deterministic_comparison()` relate to a single deterministic candidate's summary?

**Decision**: `summarize_simulation_comparison(comparison, household, reference_tax_year)` is a thin loop — `[summarize_run(run, household, reference_tax_year) for run in comparison.runs]` — with each result's `candidate_label` set from `run.candidate_label`. `summarize_deterministic_comparison(comparison, household, reference_tax_year)` is the equivalent loop over `comparison.projections`, calling a private `_summarize_plan_projection()` helper (not itself a separate public function, since `004` has no standalone "run one candidate" concept comparable to `005`'s `run_simulation()` — a bare `PlanProjection` only ever appears as one candidate inside a `ComparisonResult` or as `run_plan_projection()`'s direct return value, and this feature's spec scopes User Story 1 to Monte Carlo `SimulationRun` only, never to a standalone deterministic projection).

**Rationale**: Directly satisfies Acceptance Scenario US2.1's requirement that a comparison's per-candidate summaries "match what summarizing that single candidate's run directly would produce" — true by construction when the comparison function is literally a loop calling the single-run function, not a parallel/separate implementation that could drift from it (same Principle I concern as research.md §1).

**Alternatives considered**: A single polymorphic `summarize()` function dispatching on input type (via `functools.singledispatch` or `isinstance` branching) — rejected as unnecessary indirection for three genuinely different input shapes (`SimulationRun`, `SimulationComparisonResult`, `ComparisonResult`) that a caller already knows which one it holds; three explicitly named functions are more discoverable and match the project's existing preference for explicit dispatch (e.g. `002`'s `STATE_MODULES` dict, `003`'s `WITHDRAWAL_STRATEGIES` dict) over type-switching.

## 5. How is `unverified_figure_names` deduplicated, given `005` already deduplicates `figures_used` by `(name, last_verified)`?

**Decision**: `{f.name for f in run.figures_used if not f.verified}`, sorted into a list. A plain set-of-names comprehension, not a second `(name, last_verified)`-keyed pass.

**Rationale**: `005`'s own `_dedupe_figures()` collapses by `(name, last_verified)`, which means two entries sharing a `name` but carrying different `last_verified` dates (e.g. a figure re-cited on two different audit passes before either was resolved) could both survive `005`'s dedup and reach this feature — collapsing to `name` alone here is what Edge Cases actually asks for ("represented once in the unverified-figure list, not once per occurrence"), and a reader of `unverified_figure_names` cares about *which figures* are unverified, not how many differently-dated citations of the same figure exist.

**Alternatives considered**: Re-using `(name, last_verified)` as the dedup key here too — rejected; it would under-collapse relative to what a reader actually wants ("is `sc_bracket_table` unverified?", answered once, not once per citation date it happens to carry).

## 6. How does a Monte Carlo run's CSV export indicate, per plan-year row, whether an unverified figure was involved — given `SimulationRun.figures_used` is a run-level aggregate, not stored per plan year?

**Decision**: `run_to_csv_text()`'s per-plan-year "has unverified figure" column is derived from `run.path_results[0].years[y].figures_used` (path 0's figures for plan-year index `y`), treated as representative of every path's figures for that same plan-year index — not from an aggregate across all paths for that year.

**Rationale**: Every path within one `SimulationRun` shares an identical `plan_year → tax_year` schedule (it advances deterministically from `start_tax_year`, independent of that path's randomly drawn returns), and which `SourcedFigure`s a given tax year's federal/state tax computation consults depends on the tax year and the household's ages that year — both identical across every path for a given plan-year index — not on the dollar amounts a specific path happened to draw. So `figures_used` for plan-year index `y` is, in practice, identical across all of a run's paths; reading path 0's is exact, not an approximation of a genuinely-varying quantity. This is recorded explicitly here, and in the Constitution Check, rather than silently assumed, per Principle I's discipline for any simplification — even one that happens to be exact rather than approximate, since the *reason* it's safe (bracket-table selection depends on tax year/ages, not on drawn returns) is a fact about `002`/`003`'s design that a future reader shouldn't have to re-derive.

**Alternatives considered**: Iterating every path's `figures_used` for each plan-year row and unioning them — rejected as unnecessary O(paths × years) work for a result that's provably identical to reading one path, at reference scale (5,000 paths) turning a sub-millisecond read into meaningfully slower iteration for no behavioral difference.

## 7. How is CSV text generated, and what's the row shape for a comparison export?

**Decision**: Python's stdlib `csv.DictWriter` writing into an `io.StringIO`, returning `.getvalue()` — no new dependency (FR-012). `run_to_csv_text(run)` produces one row per plan year: `plan_year`, one column per percentile in `percentiles` (e.g. `p10`, `p25`, `p50`, `p75`, `p90`), and `has_unverified_figure` (boolean, per research.md §6). `simulation_comparison_to_csv_text()`/`deterministic_comparison_to_csv_text()` each produce one row *per candidate* — the flattened fields of that candidate's `SummaryStatistics` (`candidate_label`, `success_rate`, `ending_balance`, `median_depletion_age`, `median_lifetime_tax_paid`, and `has_unverified_figure` derived from whether `unverified_figure_names` is non-empty) — not a full per-path or per-plan-year breakdown per candidate.

**Rationale**: A single summary row per candidate is what "clearly labeled... without cross-referencing anything else" (Acceptance Scenario US3.2) calls for at human scale — a claiming-age grid comparison alone can have 81 candidates; a per-plan-year-per-candidate export would be 81 × ~36 = ~2,900 rows for that one comparison, defeating the "spreadsheet-ready, at a glance" purpose the source document's pipe-table workflow implies. A user wanting a single candidate's full year-by-year detail already has `run_to_csv_text()` available for that one run.

**Alternatives considered**: A nested/grouped CSV with one row per (candidate, plan year) pair — rejected per the row-count reasoning above; noted here as a reasonable future addition (an optional "detailed" export mode) if a future consumer specifically needs it, not a v1 requirement (FR-009 only requires "one row or row group per candidate," which a single summary row per candidate already satisfies literally).
