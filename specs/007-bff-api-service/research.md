# Phase 0 Research: BFF API Service

No items in Technical Context were left as `NEEDS CLARIFICATION` — the package layout, dependency, and offline-posture decisions all follow directly from `docs/frontend_architecture.md`'s already-completed planning session (confirmed with the user at the time). The research below resolves the feature-specific design questions this spec's Assumptions and Edge Cases raised — several of which are genuinely new ground, since this is the first feature to sit behind an HTTP boundary and the first to depend on all six prior features simultaneously.

## 1. What exactly does the `001` prerequisite (`delete_scenario()`) look like?

**Decision**: A new function in `scenario/store.py`:

```python
def delete_scenario(name: str, *, scenarios_dir: Path | None = None) -> None:
```

Deletes the named scenario's YAML file. Raises `ScenarioParseError(name, "no saved scenario named '{name}'")` if no file exists for `name` — the exact same exception type and message shape `load_scenario()` already raises for a missing scenario (`scenario/store.py`'s existing `load_scenario()` implementation). Exported from `scenario/__init__.py`'s `__all__` alongside `save_scenario`/`load_scenario`/`list_scenarios`.

**Rationale**: FR-005/FR-006 (spec.md) require a specific "no such scenario" rejection reason distinguishable from every other failure, for both a read and a remove of a nonexistent scenario — reusing `load_scenario()`'s exact existing exception class and message format means this feature's route handlers can catch one exception type across both operations, and `001`'s own test suite/contract gains an obvious, minimal, symmetric addition (delete mirrors load's error handling exactly) rather than inventing a new error shape for one new function.

**Alternatives considered**: A silent no-op delete (no error if the scenario doesn't exist) — rejected; it would make FR-006's "reports it doesn't exist" requirement unsatisfiable for the delete case, and would let a client's typo in a scenario name go unnoticed. A boolean return value (`True`/`False` for "existed and was deleted") instead of raising — rejected; every other `001` operation on a missing scenario (`load_scenario()`) already raises, and mixing raise-based and boolean-based error signaling across the same small module would be a real (if minor) API inconsistency for no benefit.

## 2. Why no results database, and what does "regenerate on demand" mean precisely for this feature's routes?

**Decision**: Every run, comparison, and export route computes its response fresh, on every call, from the request body alone (plus the named scenario `001` already persists) — no cache, no "run id" a later request references, no in-memory or on-disk store of a prior computation's result.

**Rationale**: Restates and inherits `docs/frontend_architecture.md` §5's reasoning directly: Principle II guarantees `(scenario, seed, params) → identical output`, so persisting a computed result is never a correctness requirement, and doing so anyway would introduce a cache whose true identity is really `(scenario, seed, params, code_version)` — a tax-figure correction landing in a future feature would silently leave a stale cached answer disagreeing with what current code actually produces, reintroducing exactly the ambiguity Principle II's own rationale warns against. At the measured reference-scale cost (`006`'s own benchmark: a few seconds for 5,000 paths), there is no performance case for caching either.

**Alternatives considered**: A short-lived, in-memory cache keyed by request hash, invalidated on service restart — rejected as complexity with no measured need (Performance Goals above) and a real, if narrow, staleness risk within a single service lifetime whenever a scenario is edited and re-saved under the same name between two otherwise-identical requests.

## 3. How does JSON serialization actually work, given `PercentileBand.percentiles: dict[float, float]` isn't valid JSON as a plain object?

**Decision**: `services/bff/src/rp_bff/serialization.py::to_jsonable(obj)` — a single recursive function, inherited directly from `docs/frontend_architecture.md` §3's already-worked-out design:

- `datetime.date` → `.isoformat()` (every `FigureUsage.last_verified` in every response).
- `dict[float, float]` (the `PercentileBand.percentiles` case specifically, and a general safeguard for any future non-`str`-keyed dict) → `[{"percentile": k, "value": v} for k, v in sorted(d.items())]` — array-of-objects, lossless, and the shape a future chart-drawing UI wants natively.
- `tuple` (`StrategyConfiguration.conversion_window`, `BracketTable` rows if ever surfaced) → JSON array, recursively converted.
- `dataclass` instances (the overwhelming majority of what `001`–`006` return: `Scenario`, `SimulationRun`, `PlanProjection`, `SummaryStatistics`, etc.) → recurse field-by-field via `dataclasses.fields()`.
- `list` / nested dataclass / plain scalar → recurse / pass through.

**Response-model trade-off, stated explicitly**: request bodies get real Pydantic models (`schemas.py`) for validation quality; **response** bodies for run/comparison results are `to_jsonable()` output returned as plain JSON, not hand-mirrored Pydantic response models — avoiding a large, drift-prone duplicate schema for read-only computed output that would need re-syncing every time `002`–`006` add a field. FastAPI's OpenAPI docs for these routes show a generic/`Any` response schema for v1; full response typing is reasonable future work once the shape stabilizes, not a v1 requirement.

**Alternatives considered**: Stringifying float dict keys directly (`{"0.5": 150.0}`) instead of array-of-objects — rejected per `docs/frontend_architecture.md`'s own reasoning: it's a lossy string round-trip for no benefit, and the array shape is what a chart library actually wants. Hand-authoring full Pydantic response models for every `001`–`006` return type now — rejected as premature, high-maintenance-cost work for a still-stabilizing API surface (see the response-model trade-off above).

## 4. Where do `reference_tax_year`/`start_plan_year`/`start_tax_year` come from, given `001`'s `Scenario` has no field for them?

**Decision**: All three remain **required**, non-defaulted fields on every run/comparison/export request body. Unlike `seed`/`n_paths`/`plan_to_age` (which default from the named scenario's `SimulationSettings` per FR-011), these three values have no scenario-derived default available, because `001`'s `Household`/`HouseholdMember`/`Scenario` schema was deliberately built with no "as-of" reference-year concept — `HouseholdMember.current_age` is a snapshot whose reference year every prior feature (`004`'s `run_plan_projection()` onward) has always required as an explicit caller-supplied argument, never inferred.

**Rationale**: `004`'s own `research.md` (§2, "How does a plan year's tax year map to each household member's age?") already directly rejected deriving `reference_tax_year` from the system clock: *"it would break Principle II (Reproducibility), since running the identical scenario on two different calendar dates would silently change every member's computed age."* This feature is the first to sit behind a client a real person might use on different real calendar days for the identical scenario — exactly the case that rejected alternative was written to prevent. Requiring these three fields explicitly, with no fallback, is not a gap this feature papers over; it is the same discipline `004` already established, now enforced at the HTTP boundary instead of only inside the library.

**Alternatives considered**: Defaulting `reference_tax_year` to the server's current calendar year at request time — rejected, directly contradicted by `004`'s own precedent above. Adding a `reference_tax_year` field to `001`'s `Scenario` schema so it *could* be defaulted from scenario state — considered and rejected for this feature's scope: unlike `delete_scenario()` (a small, obviously-missing, symmetric capability), adding a stateful "as-of" concept to `001`'s schema is a more significant modeling change with its own implications for `001`–`006`'s existing tests and quickstarts, better suited to a dedicated, deliberate amendment proposal than a prerequisite folded into this feature's scope.

## 5. How does the FR-018 cost estimate work, and what's the rejection threshold?

**Decision**: `services/bff/src/rp_bff/cost_estimation.py::estimate_cost_seconds(path_count, candidate_count, horizon_years)` returns `path_count * candidate_count * horizon_years * PER_UNIT_COST_SECONDS`, where `PER_UNIT_COST_SECONDS = 0.0001` (0.1ms per path-year-candidate) — a deliberately conservative multiple of the real measured per-path-year cost. A request is rejected (with the estimated cost and the budget in the error) if the estimate exceeds `REJECTION_THRESHOLD_SECONDS = 30` — half the constitution's "well under a minute" budget, leaving headroom for the HTTP/serialization overhead this estimate doesn't itself model.

**Rationale**: `005`'s own research.md §7 measured a full single-path 36-year projection at ~0.375ms — i.e. ~0.0104ms *per path-year*, not per path — and `006`'s own reference-scale benchmark (5,000 paths × 36 years, plus a 3-state 1-year comparison, combined) measured **3.77s total**. `PER_UNIT_COST_SECONDS = 0.0001` estimates that same reference-scale single run at ~18s — comfortably under the 30s threshold (so this feature's own baseline acceptance scenario, US3.1/SC-003, is never incorrectly rejected) while still ~5x more conservative than the ~3.64s it actually measured, leaving real margin for HTTP/serialization overhead the raw benchmark didn't include. **This number was verified empirically against `006`'s actual measured benchmark before being adopted** — an earlier draft of this decision used `0.001` (1ms/unit) by mistakenly treating `005`'s "~0.375ms per full 36-year projection" figure as "~0.375ms per path-year" (a 36x error); at that mistaken rate, the reference-scale single run would have estimated at 180s and been *incorrectly rejected* by this feature's own cost gate, contradicting SC-003. Caught and corrected during implementation by recomputing the estimator against `006`'s real benchmark rather than trusting the earlier arithmetic. A fixed, documented threshold — checked *before* dispatching to `005`, not discovered by a request hanging — is exactly what FR-018 asks for; 30 seconds (not 60) leaves margin so a request that's merely large, not pathological, still completes rather than being rejected right at the edge of the budget.

**Alternatives considered**: Measuring actual elapsed time and aborting mid-computation if a request runs too long — rejected; `005`'s simulation functions have no cancellation/timeout hook to abort mid-run, and building one is a materially larger change than a pre-flight estimate for a problem the estimate already solves adequately. Setting the threshold at the full 60-second budget — rejected; leaves no margin for the estimate's own known blind spots (HTTP/serialization overhead), risking a request that passes the estimate but still exceeds the real budget end-to-end.

## 6. How does a comparison request validate its candidates against current reference data, rather than surfacing a raw `KeyError` from deep in `002`/`003`?

**Decision**: Route handlers for `/simulations`, `/comparisons/deterministic`, and `/comparisons/simulated` validate `state`/`withdrawal_strategy`/`conversion_strategy` values against `STATE_MODULES.keys()`/`WITHDRAWAL_STRATEGIES.keys()`/`CONVERSION_STRATEGIES.keys()` (the same registries User Story 2's reference-data endpoints already expose) *before* calling into `004`/`005`, returning a specific rejection naming the invalid field and value if any candidate references something unregistered.

**Rationale**: FR-014 requires "a specific, actionable reason" — a `KeyError` propagating from three or four calls deep inside `002`'s `compute_state_tax()` or `003`'s `compute_withdrawal_plan()` would surface as an opaque 500-level failure with no field-level context, the same category of problem `005`'s research.md §7 already solved once for `UnsupportedTaxYearError` crossing a process boundary — this is the HTTP-boundary analog of that same lesson: an error crossing a boundary (there, a process; here, a validation layer) needs to arrive in a form the receiving side can actually act on.

**Alternatives considered**: Catching the `KeyError`/`UnsupportedTaxYearError` after the fact and translating it into an HTTP error response — rejected; it still means at least one wasted, partially-completed computation before the client learns their request was invalid, and the resulting error message would need to reverse-engineer which field caused it from an exception that doesn't carry that context. Validating up front is strictly cheaper and more precise.

## 7. How are the four comparison axes' differing candidate shapes, and the deterministic/Monte-Carlo axis mismatch, represented in one request schema?

**Decision**: Two separate route bodies (`/comparisons/deterministic`, `/comparisons/simulated`), each a discriminated-by-`axis` Pydantic model whose `candidates` field shape depends on `axis`: `list[str]` for `state` (simulated only — `004`'s `ComparisonDimension` has no `"state"` value at all, so the deterministic endpoint's schema simply has no `state` variant to select), `list[{label, conversion_strategy, conversion_bracket_ceiling_or_amount, conversion_window}]` for `roth_conversion_strategy`, `list[{label, withdrawal_strategy}]` for `withdrawal_sequencing`, and `list[dict[str, int]]` (one `{person_name: age}` mapping per grid cell) for `claiming_age_grid` — mirroring `004`/`005`'s own `compare_*()` function signatures exactly, one route body variant per function.

**Rationale**: This is a direct, literal restatement of the four `compare_*()` functions' existing parameter shapes across `004` and `005` (confirmed by direct inspection of `comparison/compare.py` and `simulation/compare.py` during this session's earlier work) — the request schema's job is to be an HTTP-shaped mirror of an already-decided function signature, not a new design. That `004` has no `compare_states()` at all (`005`'s research.md §2 built the state axis specifically because `004` never did) is what makes the deterministic/simulated split by axis, not just by engine choice, the correct shape — asking a client to select `axis="state", engine="deterministic"` and then rejecting it at request time (per FR-014) would be worse UX than the deterministic endpoint's own schema simply never offering `"state"` as a valid `axis` value in the first place.

**Alternatives considered**: One unified `/comparisons` endpoint with an `engine` field selecting deterministic vs. simulated — rejected; it would need to accept-then-reject the `state`+`deterministic` combination at runtime (a real request a client could construct and be surprised by) rather than making that combination structurally unrepresentable in the request schema, which a two-endpoint split achieves for free.
