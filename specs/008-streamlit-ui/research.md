# Phase 0 Research: Streamlit UI

No items in Technical Context were left as `NEEDS CLARIFICATION` — the UI framework, package layout, and dependency-containment decisions all follow directly from `docs/frontend_architecture.md`'s already-completed planning session (confirmed with the user at the time). The research below resolves the feature-specific design questions this spec's Assumptions and Edge Cases raised — this is the first feature in the project a person interacts with directly, and the first to consume `007`'s real, implemented contract rather than a sketch.

## 1. Does this feature depend on `retirement_planner` or `rp_bff` at all?

**Decision**: No. `apps/streamlit_ui/pyproject.toml` declares exactly three runtime dependencies — `streamlit`, `httpx`, `plotly` — and neither `retirement_planner` nor `rp_bff` (`007`'s own package) appears anywhere in it, as an editable path dependency or otherwise.

**Rationale**: `docs/frontend_architecture.md` §7 states this explicitly as the deliberate reason to build the first UI against the BFF rather than the library directly: *"it's the cheapest way to actually exercise the decoupled architecture on day one... if the first UI imported the core library directly, the BFF's contract would go untested by its only client."* This feature's own spec.md Assumptions restate the same commitment. Making the omission structural (the dependency simply isn't declared, so `import retirement_planner` would `ModuleNotFoundError` in this package's own environment) is stronger than a code-review convention — it's the same enforcement style `007` used to keep `fastapi`/`uvicorn` out of core's `pyproject.toml`.

**Alternatives considered**: Depending on `retirement_planner` anyway for convenience (e.g., to reuse its `Literal` type aliases for form validation) — rejected; it would silently reintroduce the exact coupling `007` exists to prevent, for a marginal convenience this feature doesn't need (Pydantic-free, plain-string form widgets work fine against `007`'s own reference-data responses).

## 2. How does this feature find `007`'s base URL, and what does its HTTP client look like?

**Decision**: A single environment variable, `RP_BFF_BASE_URL`, read once at app startup, defaulting to `http://127.0.0.1:8000/api/v1` (FastAPI/uvicorn's own conventional default port, since `007`'s own plan.md never pins a specific port — it only commits to binding `127.0.0.1`). `src/rp_ui/api_client.py` is a thin module of functions, one per `007` endpoint (`list_scenarios()`, `get_scenario()`, `put_scenario()`, `delete_scenario()`, `validate_scenario()`, `list_states()`, `list_withdrawal_strategies()`, `list_conversion_strategies()`, `list_comparison_axes()`, `run_simulation()`, `compare_deterministic()`, `compare_simulated()`, `export_simulation_csv()`, `export_comparison_csv()`), each a plain `httpx.Client` call against `RP_BFF_BASE_URL + <path>`, returning either the parsed JSON body or raising a typed exception (research.md §4) — no ORM-style client generation, no dependency on `007`'s OpenAPI schema at runtime (that schema is `007`'s own manual-testing surface, per its own research.md §7, not something this feature needs to consume programmatically for a v1 client this small).

**Rationale**: An environment variable is the standard, zero-dependency way to externalize a deployment-specific value (Technology Constraint: "config as data, not code"), and matches how `007` itself is expected to be started as a separate local process a user points this UI at. One function per endpoint, rather than a single generic `request()` helper exposed to every page, keeps each page script's own code reading as "what it asks for" rather than "how HTTP works" — consistent with `001`–`007`'s own preference for a small number of clearly-named public functions over one do-everything entry point.

**Alternatives considered**: Generating a client from `007`'s OpenAPI schema (`docs/frontend_architecture.md` §7 named this as what a *future* JS SPA would want) — rejected for this feature specifically; a generated client is worth its complexity for a larger or longer-lived client, and this feature's own hand-written 14 functions are simpler to read, test, and keep in sync with `007`'s contract at this project's current scale. Hardcoding the base URL — rejected; it would make this feature untestable against anything but a literal `127.0.0.1:8000`, and undeployable if `007` ever needs a different port or host.

## 3. What does the "overlay chart" (FR-009) actually show, given the two comparison engines return different data?

**Decision**: The comparison chart's shape depends on which engine produced the result, read directly from `007`'s own `SummaryStatistics.percentile_bands` field (`null` for deterministic, populated for Monte Carlo — `006`'s own documented distinction, carried through `007` unchanged): a **Monte Carlo (simulated) comparison** renders a line-overlay chart, one line per candidate, plotting each candidate's own median (50th percentile) ending balance across plan years — a genuine multi-candidate time series, since each candidate's `SummaryStatistics` carries its own full `percentile_bands`. A **deterministic comparison** renders a bar chart of each candidate's scalar summary metrics (`ending_balance`, `median_lifetime_tax_paid`) side by side — there is no time series to overlay, since a deterministic `PlanOutcome` never carried one past `004`, and `007`'s deterministic comparison response reflects that honestly (`percentile_bands: null` on every candidate).

**Rationale**: Fabricating a synthetic time series for deterministic candidates (e.g., interpolating between start and ending balance) would be exactly the kind of invented precision Principle I forbids — this feature must render what `007` actually returns, not what would look nicer. The two real, no-fabrication‑needed default channels this data already provides — a genuine per-year overlay for Monte Carlo, a genuine per-candidate bar comparison for deterministic — satisfy FR-009's "overlay chart"/US3.1 requirement for both engines without inventing anything, and Acceptance Scenario US3.3 (the "not applicable" fields must be visibly marked) is what motivated checking `percentile_bands is None` as the actual chart-shape switch rather than trusting the `axis`/`engine` selector alone.

**Alternatives considered**: Requesting `004`'s full per-year `PlanProjection` for deterministic comparisons instead of only `007`'s summarized response — rejected; `007`'s `/comparisons/deterministic` contract only returns `SummaryStatistics`, not the full `ComparisonResult`, and extending that contract is out of this feature's scope (spec.md's own scope note: any `007` contract gap becomes a small, explicit, additive amendment to `007`, not a workaround here) — there is no evidence a full per-year deterministic chart is actually needed yet, since the source document's own "compare states/strategies" framing is about outcome comparison, not year-by-year deterministic trajectories.

## 4. How does this feature translate `007`'s error responses into human messages?

**Decision**: `src/rp_ui/errors.py` defines one exception class per `007` error shape (research.md's own naming, mirroring `007`'s `contracts/bff-api.md`): `ScenarioNotFoundError`, `BlockingValidationError` (carries the flags), `UnknownReferenceValueError` (carries field/value), `CostBudgetExceededError` (carries the estimate/budget), plus a catch-all `BackendUnreachableError` for connection failures (`httpx.ConnectError`/`httpx.TimeoutException`) and `UnexpectedBackendError` for any other non-2xx response `api_client.py` doesn't recognize. Each carries enough structured data for a page script to render a specific, human-readable message (FR-007, FR-015) — e.g. `BlockingValidationError` renders every flag's own `message`, not just "validation failed."

**Rationale**: FR-007 explicitly requires each of `007`'s documented rejection reasons to produce a *distinguishable* message, not one generic error — a typed exception per shape is what makes that distinction checkable in a test (`test_errors.py`, per plan.md's Project Structure) rather than relying on string-matching a response body inline in page code. Separating `BackendUnreachableError` (can't reach `007` at all) from `UnexpectedBackendError` (reached it, got something this feature's own error mapping doesn't recognize) directly satisfies Edge Cases' "backend unreachable" case distinctly from a recognized rejection reason.

**Alternatives considered**: A single generic `BackendError(message)` carrying `007`'s raw JSON body — rejected; it would make FR-007's per-reason distinguishability a page-script-level string-matching concern instead of a type-level one, harder to test and easier to accidentally regress.

## 5. Why must `pages/` sit next to `app.py`, not under `src/`?

**Decision**: `apps/streamlit_ui/pages/*.py` are plain scripts in a `pages/` directory adjacent to the entry-point script (`app.py`) — not nested inside the `src/rp_ui/` package `001`–`007`'s own layout convention would otherwise suggest.

**Rationale**: This is a hard mechanical requirement of Streamlit's own multi-page-app feature: Streamlit discovers additional pages by looking for a `pages/` directory in the same folder as the script passed to `streamlit run`, and renders one sidebar entry per file found there, ordered by filename — this is framework behavior, not a design choice this feature is free to relocate. The *logic* those page scripts need (talking to `007`, building charts, mapping errors) still lives in the importable `src/rp_ui/` package (research.md §2 and §4's own modules), keeping every prior feature's "thin entry point, real logic in an importable package" discipline intact for everything except the two files (`app.py`, `pages/*.py`) Streamlit's own routing mechanism constrains.

**Alternatives considered**: Using Streamlit's newer `st.navigation()`/`st.Page()` API (available in recent Streamlit versions) to define pages as functions inside `src/rp_ui/` and register them from `app.py`, avoiding the `pages/` directory constraint entirely — a reasonable alternative worth naming here; not adopted for this plan only because the simpler, longer-established `pages/`-directory convention needs no further version-compatibility research to commit to now, not because the newer API is wrong. Recorded as a viable refinement for implementation to reconsider if `st.navigation()` proves cleaner in practice, without changing this feature's scope either way.
