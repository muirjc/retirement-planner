# Phase 0 Research: Advanced Tax & Benefits Modeling

No item in Technical Context was left as `NEEDS CLARIFICATION` — the harder open questions here are genuine design decisions this feature needs to make, not missing facts about the stack. Grounded in direct inspection of `tax/models.py`, `tax/federal.py`, `mechanics/models.py`, `mechanics/plan_year.py`, `comparison/projection.py`, `comparison/models.py`, and `scenario/models.py` during planning.

## 1. What counts as "investment income" for NIIT, given this engine tracks no cost basis?

**Decision**: For NIIT purposes, a plan year's investment income is approximated as that year's taxable-account withdrawal amount in full (`WithdrawalPlan.sequence_withdrawals` filtered to `account_type == "taxable"`) — the entire withdrawn dollar amount, not an estimated gain-only portion.

**Rationale**: This engine has never modeled cost basis, unrealized gains, or income character (interest vs. dividends vs. capital gains) within a taxable account — `AccountBalances.taxable` is a single number that grows by a blended return assumption (`comparison/projection.py`'s own `growth_factor` application). Building real gain-tracking would be a materially larger, separate feature (a taxable-account cost-basis model), not something this feature's scope note or FRs ask for. Treating the full withdrawal as investment income is the conservative, honest choice consistent with Principle I: it may overstate NIIT exposure for a household with a high cost basis, but it never understates it, and — critically — it's declared explicitly (in code comments, in `data-model.md`, and in every `FigureUsage`-adjacent surface this result touches) rather than presented as a precise gain calculation it isn't.

**Alternatives considered**: Modeling real cost basis and realized-gain tracking — rejected as materially out of scope for a feature spec.md itself frames as extending the *tax* engine, not adding an investment-accounting subsystem; flagged here as a natural, larger follow-on if NIIT accuracy against real cost basis ever becomes a stated need. Treating 100% of `taxable`'s account *growth* (not withdrawal) as investment income — rejected; it requires tracking basis-vs-growth split per year regardless, the same complexity as real cost-basis tracking, for a result that's no more honest than the simpler withdrawal-based proxy once both are equally approximate.

## 2. What income figure approximates MAGI for IRMAA and NIIT determinations?

**Decision**: MAGI is approximated as `ordinary_income + taxable_social_security` (the same two figures `federal.py` already computes for a plan year) — effectively this engine's own AGI, since it tracks no tax-exempt interest or above-the-line deductions.

**Rationale**: Real MAGI (for both IRMAA and NIIT) starts from AGI and adds back a small number of items (chiefly tax-exempt interest) this engine has never modeled and spec.md's Assumptions don't ask it to start now. Using the two income figures the engine already produces for every plan year keeps this feature additive — no new income-computation pass, no new field the rest of the engine has to keep in sync — and is the same honesty trade-off already made throughout `002` (e.g., `federal.py`'s own real-terms-brackets simplification): a clearly-stated approximation, not silently presented as the IRS's own MAGI.

**Alternatives considered**: Requiring users to configure tax-exempt interest as a new scenario input purely to close this gap — rejected; nothing in spec.md's scope or the source document asks for tax-exempt bond income modeling, and adding an input only to serve one internal computation's precision is exactly the kind of scope creep `002`'s own Assumptions discipline avoids elsewhere.

## 3. How does IRMAA's two-year income look-back work inside one chronological projection?

**Decision**: `run_plan_projection()`'s existing `years` list (built up chronologically, one `PlanYearProjection` appended per completed plan year) already contains everything needed: when computing plan year N's IRMAA determination, if `len(years) >= 2`, use `years[-2]`'s income figures (true two-year look-back, entirely within data this same projection has already computed). For the first two plan years of any scenario (no two-years-prior data exists within the modeled scenario), use that same year's own current income as a proxy, and record which basis was used (`"two_year_lookback"` vs. `"current_year_proxy"`) as an explicit field on the result — never silently treated as equivalent.

**Rationale**: This resolves spec.md's own Assumptions note ("a documented, explicitly flagged approximation rather than silently omitting the surcharge... the exact approximation is a planning-phase decision, not fixed here") concretely. It costs nothing extra to compute — the loop already retains prior years' results in memory — and never fabricates income history from before a scenario's own start, matching Principle I.

**Alternatives considered**: Omitting IRMAA entirely for a scenario's first two plan years — rejected; it would make a scenario whose Roth conversion bridge starts at retirement (the reference use case's own shape) blind to IRMAA in exactly the years a large conversion is most likely to trigger it. Requiring two years of pre-scenario income as a new required scenario input — rejected as disproportionate setup cost for a proxy that's already reasonable (a household's income the year before retirement starts is a defensible stand-in for "two years before this specific plan year," and it's flagged as a proxy either way).

## 4. What new scenario inputs does HSA modeling need, and how do they attach to `001`'s schema?

**Decision**: Two new, optional, additive fields:
- `HouseholdMember.hdhp_coverage: bool = False` — per-member, since HDHP coverage (the HSA-eligibility precondition) is inherently an individual fact, not a household one.
- `Scenario.hsa_contribution: HsaContributionPlan | None = None` — a household-level intended annual contribution amount, mirroring `RothConversionPlan`'s own existing optional-block shape exactly (an opaque, feature-owned block `001` stores as-is and doesn't validate beyond shape, per `001`'s own precedent for `roth_conversion`).

Both default to values that reproduce every existing scenario's current behavior exactly — `hdhp_coverage=False` and `hsa_contribution=None` mean "not modeled," so no existing saved scenario or test fixture changes behavior.

**Rationale**: This is the same "config as data, not code" extension pattern `roth_conversion` already established at the `Scenario` level in `001` — a new optional block a feature owns the interpretation of, not a validated core schema change. Per-member `hdhp_coverage` (rather than a single household-level flag) is what FR-010's "a younger spouse's eligibility is independent of the older spouse's" requirement actually needs — a household-level flag couldn't represent one spouse eligible and the other not.

**Alternatives considered**: A full HSA account balance/growth model (its own account type alongside traditional/Roth/taxable) — rejected; spec.md's own framing is explicit ("a modeled income-side constraint," not full HSA investment tracking), and the source document's own motivation (the 6-month backdating trap, the younger-spouse finding) is about *eligibility timing*, not HSA balance growth. A per-plan-year contribution schedule instead of one steady annual amount — rejected as unnecessary complexity; eligibility itself already varies year to year (computed automatically from age/coverage/Medicare status), so a single intended annual amount plus automatic per-year eligibility gating covers the real-world case (an ongoing HSA contribution habit that simply stops being eligible once Medicare starts) without asking a user to hand-schedule individual years.

## 5. What does "reject an ineligible contribution" (FR-012) actually mean inside a multi-year projection?

**Decision**: Not a hard exception that aborts the whole projection. For each plan year, HSA eligibility (and the applicable IRS contribution limit, which depends on how many household members have `hdhp_coverage=True` that year — self-only vs. family limit, plus a per-eligible-member 55+ catch-up) is computed fresh from that year's own ages/coverage/Medicare-enrollment status. The modeled contribution for that year is the lesser of the configured `annual_amount` and the year's own applicable limit, or `0.0` with a recorded reason when no household member is eligible that year at all — carried on the year's own `HsaContributionResult`, the same way a Roth conversion with no configured strategy already returns a zeroed `ConversionResult` rather than raising.

**Rationale**: A configured `hsa_contribution` naturally becomes valid in some plan years and invalid in others as household members age into Medicare — a hard exception would make every multi-year projection past that point fail outright, which nothing in spec.md's Acceptance Scenarios asks for (they describe *outcomes differing by year*, not a scenario becoming unusable). "Reject... with a specific reason" (FR-012) is satisfied by that reason being visible on the specific year's own result, exactly how every other per-year mechanics result in this engine already surfaces its own detail, rather than by an exception a caller must catch to keep a multi-year run going.

**Alternatives considered**: Raising an exception the caller must catch per year — rejected; no other per-plan-year mechanics function in this engine (RMD, withdrawal sequencing, Roth conversion) raises for an ordinary "not applicable this year" case, and introducing that pattern only for HSA would be inconsistent with `mechanics/plan_year.py`'s own established shape.

## 6. Where do the new results attach to already-existing dataclasses?

**Decision**: Additive fields only, on already-existing types:
- `PlanYearProjection` gains `irmaa: IrmaaResult`, `niit: NiitResult`, `hsa_contribution: HsaContributionResult`.
- `PlanOutcome` gains `cumulative_irmaa_paid: float` and `cumulative_niit_paid: float` — `cumulative_tax_paid`'s existing meaning (federal + state income tax only) is unchanged, so every existing test, report, and UI display that already reads `cumulative_tax_paid` keeps working unmodified; a caller that wants total household cost including surcharges sums all three fields itself.
- `tax/models.py` gains `IrmaaResult`/`NiitResult`; `mechanics/models.py` gains `HsaEligibility`/`HsaContributionResult` — placed beside `FederalTaxResult`/`StateTaxResult` and `RmdResult`/`ConversionResult` respectively, the same "one result type per mechanism, all in the subpackage's shared `models.py`" convention already in place.

**Rationale**: Additive-only fields are what let this feature reach `005-simulation-engine` and `007-bff-api-service`'s response bodies with **zero code change** in either feature (`005` because it calls `run_plan_projection()` unchanged; `007` because `to_jsonable()` recurses over dataclass fields generically — confirmed by reading `serialization.py` directly during planning). Keeping `cumulative_tax_paid`'s meaning frozen, rather than redefining it to include surcharges, avoids a silent behavior change in every downstream consumer that already reads it (`006`'s reporting, `008`'s Compare page) — an additive field is a strictly safer amendment than a redefinition.

**Alternatives considered**: Folding IRMAA/NIIT into `cumulative_tax_paid` directly — rejected; spec.md's own FR-002/FR-006 require these to be "reported separately, distinct from ordinary income tax," and silently widening an existing figure's meaning would violate that FR for every caller that doesn't yet know to expect it.

## 7. Reference figures for the new numeric primitives

**Decision**: Following `federal.py`'s own precedent exactly — an illustrative, `verified=False` `SourcedFigure` schedule for each new figure (IRMAA tier thresholds/surcharge amounts by filing status, the NIIT threshold by filing status plus its 3.8% rate, HSA self-only/family contribution limits plus the 55+ catch-up amount), each carrying a citation string naming the real primary source it should eventually be checked against (CMS.gov's IRMAA tables; IRC §1411 for NIIT; IRS Rev. Proc. for HSA limits) and `last_verified` set to today's date, honestly reflecting that verification hasn't happened yet.

**Rationale**: Matches this project's own established, repeated precedent (`federal.py`, `bracket_math.py`'s state modules, `rmd.py`'s divisor tables) — a placeholder figure is always structurally complete and honestly flagged, never a silently-omitted feature. Unit tests for each new primitive are written against these same illustrative figures (hand-calculated expected results), per the constitution's own "Unit test coverage for numeric primitives" gate — cross-checking against the real primary sources named in each citation is follow-on work this feature flags, not blocks on.

**Alternatives considered**: Leaving figures unset/`None` until real numbers are sourced — rejected; every existing tax figure in this project ships with a structurally real, clearly-flagged placeholder from day one specifically so the engine is testable and usable immediately, with verification tracked separately (per the constitution's own residual-backlog precedent already used for `002`/`003`'s own bracket figures).
