# Contract: UI Pages (addendum to `008`)

Extends `specs/008-streamlit-ui/contracts/ui-pages.md`'s `pages/1_Scenarios.py` section only — `app.py`, `pages/2_Run_Simulation.py`, and `pages/3_Compare.py` are unaffected (they consume a saved, already-`is_usable` scenario by name; they never render or submit account data themselves).

## `pages/1_Scenarios.py` — Scenario management (updated)

**Correction found during implementation**: `008`'s actual shipped form (not its original contract draft) already deviated from "an accounts section (add/remove entries, each with type/balance)" — it renders exactly one fixed number input per account type (`traditional_balance`/`roth_balance`/`taxable_balance`), matching the form's existing "household size is fixed to 1 or 2, no free-form add/remove list" convention (`008`'s module docstring). Given that, owner is captured **structurally**, not via a dropdown: the three account-type inputs are duplicated per household member (`member1_traditional_balance`/`member1_roth_balance`/`member1_taxable_balance`, and — only when `filing_status` is `married_filing_jointly` — the same three again for `member2_*`), mirroring the form's existing `member1_*`/`member2_*` field-naming pattern for household data exactly. This still satisfies FR-007 ("choose from the household's actual configured members, not free-text entry") — more strongly than a dropdown would: an account's owner is exactly whichever member's row a value was entered in, so an invalid owner is structurally impossible, not merely disallowed by a validator. For a single-member household, only the `member1_*` fields render at all (no second row to choose from, matching FR-003 / research.md §3's parse-time auto-fill precedent).
- **Modified error rendering**: the existing inline `validation_flags` rendering (`008`'s FR-002 behavior, unchanged mechanism, listing every flag with its `field`/`message`/`severity`) now also covers the two new `accounts[i].owner` flags (`scenario-api.md`, this feature) exactly like every other flag already renders. In practice, because owner is now always structurally supplied by this form (a value in `member1_*`/`member2_*` always carries an explicit, current, correctly-spelled owner — see above), neither owner flag can actually be produced by a scenario this form itself saved; they remain reachable only via a scenario authored outside this UI (raw YAML, a direct API call, or a pre-existing scenario loaded and re-saved without correction) — the same "no new UI machinery needed, the existing renderer already handles it" story as every other flag.
- **Modified *Load existing* behavior**: loading a scenario matches each returned account to a `member1_*`/`member2_*` row by `(account_type, owner)` against the currently-loaded members' `person_name`s. An account whose `owner` is `None` or doesn't match either loaded member (a multi-member scenario saved before this feature, or a stale reference after a rename) is not placed into any row — its balance is not silently guessed into a row it may not belong to (FR-006's discipline applied to the read path too). **Correction found during implementation**: because this form's `owner` is always structurally supplied on submit (every row always carries an explicit, current member name — see above), an unmatched account's *blocking validation flag* is not what actually resurfaces on the next *Save*/*Validate* — resubmitting without noticing would send a fully owner-valid body and validate cleanly. The real, and correct, signal is that the unmatched balance itself is visibly absent (shows as its `DEFAULTS` zero in every row) rather than the real figure the user expects to see — a self-evident "this didn't load" cue that prompts the user to re-enter it under the correct member before saving, rather than a validation error appearing after an unedited resave. `008`'s *Load* action (`get_scenario()`) does not itself call *Validate*, and no new auto-validate-on-load behavior is introduced by this feature.

Every other `pages/1_Scenarios.py` behavior `008` already documents (scenario-name field, household add/remove, spending field, state selector, market-assumptions section, simulation-settings section, optional Roth-conversion section, *Save*/*Validate*/*Delete* actions, `ScenarioNotFoundError`/`InvalidScenarioError`/`BackendUnreachableError` handling) is unchanged.

## Consumption expectations for a future second UI

Unchanged from `008`'s own note: this contract maps directly onto `007`'s request/response contract (`bff-api.md`, this feature's addendum) — a future non-Streamlit UI builds its own account-owner control against `AccountRequest.owner` the same way.
