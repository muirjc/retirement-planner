# Phase 0 Research: Per-Owner Account Attribution

No item in Technical Context is `NEEDS CLARIFICATION` — language, dependencies, storage, testing, platform, and performance posture all carry forward unchanged from `001`–`010`. The research below resolves the two design questions the spec's Assumptions section deliberately left open, plus the mechanical questions that fall out of tracing this change through every layer it touches.

## 1. Does fixing RMD attribution require tracking each member's account balance independently through the whole multi-year projection?

**Decision**: No. `run_plan_projection()` (`004`) keeps its single pooled `AccountBalances` as the only balance state it carries year to year — withdrawal sequencing, Roth conversion, tax-funding withdrawals, and investment growth all continue to operate on household-level pooled totals per account type, byte-for-byte the same arithmetic as today. What changes is only how the year's *total* RMD dollar amount is derived: instead of attributing the household's entire pooled traditional balance to one deemed owner, each household member's own RMD is computed from `member_share × pooled_traditional_balance`, where `member_share` is that member's fraction of the household's traditional balance *as configured at scenario entry*, held fixed for the life of the projection. The household's total `rmd_amount` fed into `compute_plan_year_mechanics()` is the sum of the (0, 1, or 2) members' individually-computed RMDs — each using that member's own age and own share-derived balance against `003`'s already-correct `compute_rmd()`.

**Rationale**: A genuinely dynamic per-member balance (tracking each member's own traditional/Roth/taxable balance separately, drawn down independently by withdrawals and conversions) runs into a real modeling problem, not just extra bookkeeping: a Roth conversion moves dollars from *a specific member's own* traditional balance into *that same member's own* Roth balance, but `001`'s schema records no cost basis, no lot-level detail, and no per-member withdrawal preference — there's no principled way to decide whose traditional dollars funded this year's household spending draw or this year's conversion without inventing a rule the spec's Assumptions explicitly didn't ask for. A pooled-then-scaled-by-fixed-share approach sidesteps this cleanly: it fixes exactly the accuracy gap the spec's User Story 1 names (each member's *own age* against *their own share* of the balance drives their own RMD-required-starting year and divisor) while changing nothing else about the engine's already-tested, already-correct pooled arithmetic. It is also trivially reproducible (Principle II) — the share is a pure function of the scenario's initial account data, computed once, never re-derived from randomness or engine state.

**Alternatives considered**:
- *Full per-member balance tracking with a withdrawal/conversion attribution rule* (e.g., pro-rata by each member's current share) — rejected: breaks down exactly where a conversion or a fully-depleted account type has no existing per-member base to scale against (a $0-balance Roth receiving its first-ever conversion has no ratio to apply), and would require inventing new draw-order semantics the spec didn't ask for and Principle I would require flagging as a real behavioral assumption rather than the "same arithmetic, better attribution" story this decision tells.
- *Splitting the traditional balance evenly (50/50) between members every year regardless of actual ownership* — rejected: this is exactly what `004`'s research.md §4 already rejected for the deemed-owner design and remains wrong for the same reason (invents an ownership split the data doesn't support, now made worse since real per-account ownership data exists and would go unused).
- *Recomputing each member's share every plan year from that year's actual running balances* — rejected: without a per-member balance to derive the share from (see above), there's nothing to recompute it from; this alternative only makes sense if full per-member tracking (rejected above) is also adopted.

## 2. Where is `member_share` computed, and what is its exact contract?

**Decision**: `services/bff`'s `resolution.py` computes it (the same module that already turns `scenario.accounts` into the pooled `AccountBalances` `resolve_run_context()` returns), as a new `traditional_ownership_shares: dict[str, float]` — one entry per household member, keyed by `person_name`, values summing to `1.0` whenever the household's total initial traditional balance is positive. When that total is `0.0` (no traditional accounts at all), every member's share is `0.0` — safe because `compute_rmd()` already returns a zero RMD for a non-positive balance regardless of share, and because nothing in this engine ever adds new principal to the traditional balance (only investment growth on an existing balance, or a Roth conversion moving money *out* of it) — a pooled traditional balance that starts at `0.0` can mathematically never become positive later in the same projection, so the share's fixed-at-zero value never becomes stale.

`run_plan_projection()` (and, transitively, `run_simulation()` and every `comparison.compare_*()`/`simulation.compare_*()` function) receives this dict as a new required parameter and does not itself validate it — consistent with how these functions already trust `accounts: AccountBalances` and `household: Household` as pre-validated caller input (`003`'s and `004`'s own docstrings: value-level plausibility is `scenario.validation`'s job, not the compute layer's). The one exception, mirroring `005`'s existing `survival_curves` precedent (`run_simulation()`'s FR-018: "Raises `KeyError` if `survival_curves` is given but omits a household member's `person_name`... validated eagerly, before any path is scored"): `run_plan_projection()` raises `KeyError` eagerly, once, if `traditional_ownership_shares` omits any of `household.members`' names — the identical fail-fast shape this codebase already uses for exactly this class of caller mistake, not a new pattern.

**Rationale**: `resolution.py` is already the single seam where `Scenario`-shaped, owner-aware data (`scenario.accounts`) is translated into the pooled, owner-blind shape (`AccountBalances`) the compute layer consumes — adding the share computation there, alongside the existing `_sum_accounts()`-equivalent, keeps that translation in one place rather than duplicating "walk `scenario.accounts` and total by type/owner" logic in two spots. Threading the result as an explicit parameter (never re-derived inside `run_plan_projection()` from a `Scenario` object it doesn't have — `004`/`005` intentionally know nothing about `001`'s `Scenario` type, only about `Household`/`AccountBalances`, per `004`'s existing layering) preserves the existing dependency direction: `scenario` (`001`) knows nothing about `comparison`/`simulation`; `comparison`/`simulation` (`004`/`005`) know nothing about `scenario`'s `Account`/YAML shape, only about the plain data `resolution.py` (`007`) hands them.

**Alternatives considered**:
- *Passing `list[Account]` itself into `run_plan_projection()` instead of a pre-summed share dict* — rejected: would make `004`/`005` depend on `001`'s `Account`/`Scenario` types, breaking the existing layer boundary (`004`'s own Constitution Check already treats `scenario`, `tax` → `mechanics` → `comparison` as a strict one-directional layer order); a plain `dict[str, float]` is exactly the same "opaque, pre-resolved data" shape `accounts: AccountBalances` and `strategy: StrategyConfiguration` already are.
- *Silently defaulting an omitted member's share to `0.0` instead of raising `KeyError`* — rejected: would silently zero out a real member's RMD if a caller's dict construction has a typo or omission, exactly the kind of silent wrong-number Principle I forbids; failing loudly and immediately, matching the `survival_curves` precedent, is safer and cheaper to debug.

## 3. Should the account-ownership field be a hard parse error or a value-level validation flag when missing/invalid?

**Decision**: A value-level `ValidationFlag` (severity `blocking`), produced by `scenario.validation.validate()` — not a `ScenarioParseError` raised by `scenario.loader.parse_scenario()`. `Account.owner` becomes `str | None = None` at the dataclass level (parse-time optional); `parse_scenario()` auto-fills it with the sole member's `person_name` whenever the household has exactly one member and the YAML's account entry omits `owner` (FR-003) — no existing single-filer scenario file needs a single edit. `validate()` then adds a blocking flag for any account whose `owner` is still `None` after parsing, and a second blocking flag for any account whose `owner` doesn't match any of `scenario.household.members[*].person_name` (covers both a married household that omitted the field and any household with a stale/misspelled owner after a member rename) — both cases point at the specific `accounts[i]` index and a human-readable message, following `_validate_accounts()`'s existing per-account-index pattern exactly (FR-002, FR-006).

**Rationale**: Every other "this value is present in the YAML but semantically wrong" problem this codebase has (a negative balance, an out-of-range claiming age, spending that outstrips assets) is a blocking/warning `ValidationFlag`, never a hard parse failure — `Scenario` still constructs, `is_usable` goes `False`, and the BFF/UI's existing "show every flag inline, let the user fix and re-save" flow (already built for `007`/`008`) handles it with zero new UI machinery. Routing this through `ScenarioParseError` instead would be the only field in the whole schema where a missing value blocks construction entirely rather than surfacing as a flag, breaking that consistency for no benefit — the spec's own Edge Cases describe this case in flag language ("the tool must flag this account clearly"), not load-refusal language.

**Alternatives considered**:
- *`ScenarioParseError` for a missing/mismatched owner* — rejected for the consistency reason above; it would also be a strictly worse user experience through the BFF (a 422 with no `validation_flags` list to render inline, versus the existing pattern the UI already knows how to display).
- *Making `owner` required at parse time for every household size (no single-member auto-fill)* — rejected: directly contradicts FR-003 ("no additional owner selection... automatically and unambiguously attributed") and would force every existing single-filer scenario file to be hand-edited before it loads again, which the spec explicitly rules out ("Existing single-owner scenarios (single filers) are unaffected in behavior").

## 4. Does `reporting/aggregation.py`'s existing `deemed_rmd_owner()` usage need to change?

**Decision**: No. `deemed_rmd_owner()` and `member_age_in_tax_year()` (both public in `comparison/__init__.py` since `006`) stay exactly as they are and keep their current name and behavior. `006`'s only use of `deemed_rmd_owner()` is to pick a reference member's *age* for translating a shortfall plan-year into a human-readable age label in a summary report (`reporting/aggregation.py:40-41`) — it is never used to size an RMD dollar amount there. This feature's fix is entirely inside `run_plan_projection()`'s own RMD computation (research.md §1); `deemed_rmd_owner()` remains available, unmodified, for this unrelated age-labeling purpose.

**Rationale**: Renaming or removing a function still doing real, correct work for a different, unrelated purpose (a display label, not a dollar computation) would be pure churn with no accuracy benefit, and would touch `006`'s locked contract for no reason this feature needs.

**Alternatives considered**: Renaming `deemed_rmd_owner()` to something that no longer implies "the member whose RMD this is" (e.g. `older_member()`) — rejected as unnecessary churn; its docstring already scopes it to "the older household member... treated as the deemed owner... for RMD purposes" which remains one accurate (if narrower, post-this-feature) description of what `006` actually uses it for, and updating a docstring is a one-line implementation-phase task, not a contract change.

## 5. Does this feature change any figure requiring a citation (Principle III)?

**Decision**: No. This feature introduces no new tax rate, threshold, or legal figure — `compute_rmd()`'s existing `RMD_START_AGE`, `UNIFORM_LIFETIME_TABLE`, and `JOINT_LIFE_TABLE` `SourcedFigure`s (`003`) are consumed exactly as before, once per owning member instead of once per household. No new `SourcedFigure` or citation is required.

## 6. Migration path for scenario files saved before this feature

**Decision**: No automated migration script ships with this feature. A pre-existing multi-member (MFJ) scenario file with accounts that predate the `owner` field surfaces the blocking `ValidationFlag`s from research.md §3 the next time it's loaded or validated — through the CLI-less library (`load_scenario()`), the BFF (`GET`/`PUT /scenarios/{name}`, `POST /scenarios/{name}/validate`), or the Streamlit UI's Scenarios page, which already renders every blocking flag inline with a field reference. The user adds the missing `owner:` value per account (in the YAML directly, or via the UI's new per-account owner picker — User Story 2) and re-saves; from then on the scenario loads and computes normally. A pre-existing single-filer scenario file needs no action at all (research.md §3's auto-fill).

**Rationale**: This is the smallest change that fully satisfies FR-006/SC-002 (no silent guess, a specific actionable message) without building and testing a separate one-off migration tool for what — given `001`'s enforced 1-or-2-member household cap — is at most a handful of `owner:` lines per affected file. The existing validate-then-fix loop (already built for every other blocking flag this tool has ever introduced, including `010`'s own new fields) is the tool's one general mechanism for "this scenario needs a human decision before it's usable" — reusing it here is consistent with Principle IV (extensibility through existing interfaces) rather than adding a second, parallel mechanism.

**Alternatives considered**: A `bd`-adjacent or standalone CLI migration script that rewrites saved YAML files to guess/assign owners automatically — rejected outright per the spec's explicit FR-006 ("MUST NOT silently assign, guess, or default an owner"); any automated assignment for a 2-member household is a guess by definition, since `001`'s pre-existing data has no signal at all about which member actually owns which balance.
