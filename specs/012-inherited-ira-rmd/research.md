# Phase 0 Research: Inherited IRA (Already-in-RMD-Status) Modeling

This is a research/design pass, originally prompted by `rp-2cs`: *"Plan out how to include inherited IRAs that are already in RMD"* — i.e., the original account owner has died, the beneficiary has already begun mandatory distributions, and the tool's existing RMD logic (`compute_rmd()`, `003-retirement-account-mechanics`, sized per-owner via `011-per-owner-accounts`' `traditional_ownership_shares`) has no concept of this at all: it only ever computes a *living* owner's own RMD against the Uniform Lifetime Table. No item below is left as `NEEDS CLARIFICATION`; every design question `rp-2cs`'s own description raises is resolved. §1–§9 were written before `spec.md` existed, grounded directly in `rp-2cs`'s own text (quoted where relevant) and in `003`/`004`/`011`'s established precedent rather than in FR numbers; `spec.md` (FR-001–FR-011) has since been written from these decisions via `/speckit-specify`. §10 is an addendum, added during `/speckit-plan`, closing a small number of integration-level questions Phase 1 design surfaced that §1–§9 did not need to answer — two of §10's decisions (traditional-account-only scope; Monte Carlo exclusion) were significant enough to also be reflected back into `spec.md` as FR-012/FR-013, once Phase 1 design surfaced them as real user-facing scope boundaries rather than pure implementation detail.

The slot `012` is used for this design pass's artifacts (`specs/012-inherited-ira-rmd/`); implementation is explicitly out of scope for `rp-2cs` (see the bead: *"Out of scope for this bead: actual implementation — this is the planning/design task only"*) and is left for a future bead to run `/speckit-specify` against.

## 1. Does modeling this feature require the simulation to represent a death event, or only a pre-existing inherited state?

**Decision**: The original owner's death, and the beneficiary's inheritance, are always modeled as having occurred **before** the scenario's `t=0` (i.e., before `simulation_settings`' effective `reference_tax_year`). The decedent is never itself a `HouseholdMember` — `HouseholdMember` continues to describe only living people the plan is being built around. Only the beneficiary (who may or may not be a current `HouseholdMember`, see §8) is represented. Modeling a mid-projection death event — a household member dying in, say, plan year 7, triggering a household-composition change and a *new* inherited account appearing partway through the horizon — is out of scope for this bead and named as follow-on work (§9.10).

**Rationale**: `rp-2cs`'s own framing — *"an inherited IRA that is already in RMD status"*, *"the beneficiary has already begun mandatory distributions"* — describes a pre-existing condition of the scenario being modeled, not an event the simulation itself needs to trigger. This mirrors the scoping discipline `004`'s and `011`'s research.md both use: model exactly the case named, name everything else explicitly rather than silently half-supporting it (Constitution Principle I — never present a guessed simplification as a real determination).

**Alternatives considered**: Modeling in-simulation death as a triggerable event that converts an owned account into an inherited one mid-projection — rejected as a materially larger, structurally different feature. It would touch `011`'s `traditional_ownership_shares` (computed once, fixed for the life of the projection per `011`'s research.md §2), `005`'s survival-curve machinery, and `006`'s reporting/age-labeling, all at once; conflating it with this bead's narrower "already inherited, already in RMD" scope would blur two independently-sizable design problems into one under-researched pass.

## 2. Scope boundary: does this cover every inherited-IRA case, or only the owner-died-after-RBD case?

**Decision**: This research — and the implementation feature it feeds — covers **only** the case where the original owner died **on or after** their Required Beginning Date (RBD), i.e. `decedent_was_taking_rmds=True`. Under the SECURE 2.0 "at least as rapidly" rule, this is the case requiring an annual RMD in *every* year of the 10-year window, sized off a continuing life-expectancy divisor — exactly the case `rp-2cs` names: *"with annual RMDs required within that window if the original owner had already started their own RMDs (the 'already in RMD' case this bead is about)."* The case where the owner died **before** their RBD — no annual RMDs required in years 1–9, only full depletion required by year 10 — is explicitly **out of scope** (§9.1). The field `decedent_was_taking_rmds: bool` is still modeled as a real field, not omitted, precisely so a `False` value can be caught by a blocking `ValidationFlag` (§6) rather than silently mishandled by code that only implements the `True` path.

**Rationale**: `rp-2cs`'s title and body both anchor on "already in RMD status" — this is the bead's own explicit scope, not an inferred narrowing. Splitting pre-RBD vs. post-RBD death into separate research/implementation passes keeps each pass's branching complexity independently reviewable, the same way `004`'s research.md §3 scoped the Joint Life Table gap narrowly (spousal, >10-years-younger only) rather than trying to resolve every RMD edge case in one feature.

**Alternatives considered**: Researching both post-RBD and pre-RBD death in one pass — rejected; the two cases have genuinely different annual-obligation logic (RMD-every-year vs. no-RMD-until-year-10), and conflating them risks exactly the kind of unstated-assumption blur Principle I forbids. Better to design one well-reasoned case fully and flag the other explicitly than to design both shallowly.

## 3. How should beneficiary type be modeled, given EDBs are exempt from the 10-year rule?

**Decision**: Model beneficiary status with two orthogonal fields, not one flattened enum:

- `beneficiary_relationship: Literal["spouse", "minor_child", "other_individual", "trust_or_entity"]` — descriptive/audit metadata about who the beneficiary is.
- `beneficiary_classification: Literal["eligible_designated_beneficiary_spouse", "eligible_designated_beneficiary_other", "non_eligible_designated_beneficiary"]` — the field the RMD compute layer actually branches on.

Only `beneficiary_classification == "non_eligible_designated_beneficiary"` (the SECURE 2.0 10-year-rule case — `rp-2cs`'s own "most non-spouse beneficiaries") gets full annual-RMD computation in the feature this research feeds (§5, §7). The two EDB values are recognized as real, storable data (so this taxonomy doesn't need re-litigating by a future feature) but their actual divisor/stretch/rollover computation is explicitly deferred: a spouse beneficiary who has *not* rolled the inherited account into their own IRA still needs inherited-account modeling of some kind (a spousal rollover exits this model entirely and becomes an ordinary `compute_rmd()`-owned account instead — §9.2), and non-spouse EDBs (minor child, disabled/chronically-ill, <10-years-younger) need their own life-expectancy-stretch logic against a different divisor rule than the 10-year case (§9.3). Both are named follow-on work, not silently unhandled.

**Rationale**: `rp-2cs` explicitly asks for a beneficiary-type distinction and explicitly notes EDBs have different options "not subject to the 10-year rule" — collapsing this to a single boolean would erase exactly the relationship detail a future EDB-stretch feature would need to reconstruct from scratch. This directly mirrors `004`'s research.md §3 pattern: model the fact explicitly, implement the conservative/primary case now, name the rest as an open, flagged gap rather than guessing or omitting the field (Principle I).

**Alternatives considered**: A single `is_ten_year_rule: bool` — rejected, discards the relationship/classification detail `rp-2cs`'s own text asks for. A single fully-granular `Literal` merging relationship and classification into one value (e.g. `"minor_child_edb"`, `"disabled_edb"`, `"spouse_edb"`, `"non_edb"`) — rejected as harder to extend later: adding a new relationship subtype (e.g. splitting "disabled" from "chronically ill") would force renaming existing classification values, whereas two orthogonal fields keep "who they are" and "which rule applies" independently extensible.

## 4. How does an inherited account fit into the `Account`/`Scenario` data model, given this is "a new account classification, not just a new RMD divisor" (rp-2cs)?

**Decision**: Add `Account.inherited: InheritedIraDetails | None = None` — a new optional field, default `None`, so every existing scenario file continues to parse unchanged (the same non-breaking pattern `011`'s research.md §3 used when it added `owner: str | None = None`). `Account.account_type` stays exactly `Literal["traditional", "roth", "taxable"]`, **unmodified** — inherited-ness is orthogonal to tax treatment; a Roth inherited IRA must still be `account_type="roth"` so `002`'s and `003`'s existing Roth tax-treatment logic keeps applying to it. `InheritedIraDetails` is a new, separate dataclass (see §7's sketch), alongside `Account`/`RothConversionPlan`/`HsaContributionPlan` in `scenario/models.py` — no dataclass subclassing. `Account.owner` (from `011`) continues to mean "the person this account's ownership/attribution is keyed to" — for an inherited account this is the **beneficiary's** `person_name`, not the decedent's; no separate `beneficiary_name` field is introduced, since `owner` already carries exactly that role.

**Rationale**: No dataclass inheritance exists anywhere in `scenario/models.py` today — every variant concept, including `011`'s own `owner` addition, is a flat optional field or a small sibling dataclass, never a subclass; this decision follows that established pattern rather than introducing a new one. Keeping `account_type` unforked avoids fanning a new enum value out through every existing `account_type ==` match arm across the codebase (confirmed by inspection: `comparison/projection.py:241`, `mechanics/plan_year.py:72`, `mechanics/withdrawal_sequencing.py:59-66`, `services/bff/src/rp_bff/resolution.py:99,114`, `scenario/store.py:63`, `scenario/loader.py:122`, `scenario/validation.py:36`, `services/bff/src/rp_bff/schemas.py:38`) — a forked `"inherited_traditional"` value would need *both* the fork's new arm *and* the ordinary traditional-tax-treatment logic simultaneously wherever tax treatment (not inherited-ness) is what actually matters, which a forked enum can't express cleanly. §9.11 lists these exact call sites as what a future implementation bead must touch for the field additions in this decision (the inherited-specific balance/RMD/deadline logic itself, per §7, needs its own new call sites, not modifications to these).

**Alternatives considered**: A new `account_type` value, e.g. `"inherited_traditional"` — rejected; breaks the "orthogonal to tax treatment" property (has no analog for an inherited Roth account) and forces every existing `account_type ==` switch arm listed above to add a new case even where the underlying tax treatment is unchanged. Dataclass subclassing (`class InheritedAccount(Account): ...`) — rejected; no precedent anywhere in this codebase, and would complicate `scenario/loader.py`'s existing flat-dataclass parsing and `scenario/store.py`'s flat-dataclass serialization, both of which assume one uniform `Account` shape.

## 5. Can an inherited account share `011`'s pooled `traditional_ownership_shares` mechanism, or does it need independent balance tracking?

**Decision**: No — inherited accounts are excluded entirely from `011`'s pooled `AccountBalances.traditional` total and from `traditional_ownership_shares`. The resolution-layer share computation (`services/bff/src/rp_bff/resolution.py`'s `_sum_accounts()`/`_traditional_ownership_shares()`-equivalents) must filter to `account.inherited is None` when building both the pooled total and each member's share. Each inherited account instead needs its own independently-tracked balance, carried through the projection loop keyed by a stable per-account identity (§8), never commingled with the beneficiary's own traditional balance or with any other inherited account.

**Rationale**: IRS rules forbid commingling an inherited IRA with the beneficiary's own IRA (or with a different decedent's inherited IRA) — a withdrawal from one has zero legal bearing on another's RMD obligation or 10-year clock. `011`'s research.md §1 justified its own "no full per-member dynamic balance tracking" shortcut specifically by an *unsolvable* attribution problem: no cost-basis or lot-level data exists to say whose dollars funded a shared pooled withdrawal or conversion. That ambiguity does not exist here — an inherited account is, by law, never shared with anything from the moment it's inherited, so its balance is unambiguous from the moment `Account.balance` is set at scenario-definition time; there is no pooling shortcut to justify. Reusing `011`'s pooling mechanism for an inherited account would misrepresent both its RMD divisor (must be decedent/beneficiary-specific per Single Life Expectancy Table, §7, not Uniform Lifetime) and its 10-year depletion deadline (no analog exists for an ordinary owned account) — this would be a Principle I violation (a silently wrong, decision-relevant dollar figure), not a harmless simplification.

**Alternatives considered**: Pooling the inherited balance into the household's ordinary traditional total and sizing its RMD via `011`'s member-share mechanism — rejected outright; this would be legally incorrect modeling, not merely an approximation, since it applies the wrong divisor table and silently drops the 10-year deadline altogether.

## 6. New validation rules

**Decision**: Three new blocking `ValidationFlag`s, added in `scenario/validation.py` alongside `011`'s existing per-account-index owner checks:

1. `account.inherited is not None and account.inherited.decedent_was_taking_rmds is False` → blocking flag naming the pre-RBD case as unsupported (§2).
2. `account.inherited is not None and account.inherited.beneficiary_classification != "non_eligible_designated_beneficiary"` → blocking flag naming the specific EDB/spousal case as unsupported (§3).
3. `account.inherited is not None and account.owner is None` → blocking flag; an inherited account still needs a beneficiary `owner`, using the exact rule `011` already enforces for every other account (`011`'s research.md §3).

Each flag follows `_validate_accounts()`'s existing pattern exactly: points at the specific `accounts[i]` index, gives a human-readable message naming the unsupported case, and is `blocking` (never a load-refusing `ScenarioParseError` — `011`'s research.md §3's reasoning for why value-level semantic problems are flags, not parse errors, applies identically here).

**Rationale**: Every out-of-scope case named in §2/§3/§9 must be *caught and surfaced*, not silently computed wrong or silently ignored — this is the same "flag explicitly, never silently guess" discipline (Principle I) that governs every other value-level constraint this codebase enforces, and it's what lets `InheritedIraDetails` safely model fields (`decedent_was_taking_rmds`, `beneficiary_classification`) whose full range isn't yet computable.

**Alternatives considered**: Narrowing the dataclass fields' types so only supported values are representable (e.g., a `Literal["non_eligible_designated_beneficiary"]` instead of the full three-value `Literal`) — rejected; this would make the taxonomy itself useless as forward-looking storage (§3's whole point) and would force a breaking type change on every future feature that adds EDB support, instead of just relaxing a validation rule.

## 7. RMD computation: new function, new module, new figure

**Decision**: A new sibling module, `mechanics/inherited_rmd.py`, parallel to `mechanics/rmd.py`, exposing:

```python
def compute_inherited_rmd(
    inherited_balance: float,
    tax_year: int,
    death_year: int,
    decedent_age_at_death: int,
    decedent_was_taking_rmds: bool,
    beneficiary_classification: Literal[
        "eligible_designated_beneficiary_spouse",
        "eligible_designated_beneficiary_other",
        "non_eligible_designated_beneficiary",
    ],
) -> InheritedRmdResult:
```

`InheritedRmdResult` (new dataclass in `mechanics/models.py`, sibling to `RmdResult`): `required_amount: float`, `table_used: Literal["single_life_expectancy"] | None`, `divisor: float | None`, `figures_used: list[FigureUsage]`, plus two fields with no analog in `RmdResult` — `depletion_deadline_year: int` and `is_within_ten_year_window: bool` (see §8 for how the deadline is enforced downstream).

A new `SINGLE_LIFE_EXPECTANCY_TABLE: SourcedFigure[dict[int, float]]` (IRS Pub. 590-B Table I), built with the exact `name`/`schedule`/`citation`/`last_verified`/`verified=False` shape `rmd.py`'s three existing figures use. Ships with partial, illustrative divisor coverage — following `JOINT_LIFE_TABLE`'s own "partial coverage, explicitly flagged" precedent (`rmd.py`'s module docstring: *"JOINT_LIFE_TABLE covers only the age pairs this project's tests and quickstart.md exercise; extending coverage... is follow-on work, not something this feature hides"*) — never presented as complete (§9.8).

Divisor arithmetic for the in-scope case (`beneficiary_classification == "non_eligible_designated_beneficiary"`, `decedent_was_taking_rmds == True`): look up the decedent's Single Life Expectancy divisor at `decedent_age_at_death` for the tax year immediately following death, then apply the IRS "reduce the divisor by exactly 1.0 for each subsequent year" rule — `divisor = initial_divisor - (tax_year - (death_year + 1))` — **not** a fresh table lookup keyed by the beneficiary's own current age each year. Guard `divisor <= 0` as a data/logic error to raise loudly on: a correctly-modeled 10-year forced depletion should never let the annual-RMD portion of the window run past the divisor's natural expiry, since §8's forced full-depletion draw fires no later than `death_year + 10`.

**Rationale**: `compute_rmd()`'s signature is a locked contract (`specs/003-retirement-account-mechanics/contracts/mechanics-api.md`), already consumed by `004`'s and `011`'s call sites in `comparison/projection.py`. Widening it with inherited-account parameters or internal branches would force every existing caller to pass a meaningless default, and would conflate two conceptually and legally distinct computations — a living owner's own RMD, versus a decedent's account's forced depletion schedule — inside one function's control flow, harder to unit-test in isolation. Constitution Principle IV calls for exactly the alternative chosen here: a new, documented extension point (a sibling module and function), not a widened core function. The "subtract 1 each year" divisor rule (rather than a fresh lookup) is the IRS's actual method for this specific already-in-RMD, non-EDB case per Pub. 590-B — a fresh-lookup-each-year approach would silently misstate later years' required amounts.

**Alternatives considered**: Adding a `beneficiary_type` parameter with internal branching inside `compute_rmd()` itself — rejected for the contract-breakage and conflation reasons above. Recomputing the divisor from the table fresh each year (keyed by the beneficiary's current age, the way a living owner's own RMD works) instead of the "subtract 1" rule — rejected as the wrong IRS rule for this case, and one that would silently produce a wrong dollar figure in every year after the first.

## 8. Interaction with the multi-year projection loop and the hard 10-year depletion deadline

**Decision**: `depletion_deadline_year = death_year + 10`, computed once at resolution time and held fixed for the life of the projection — mirroring `011`'s research.md §2 "computed once, never re-derived" pattern for `traditional_ownership_shares`. Each plan year, in addition to `compute_inherited_rmd()`'s annual required amount, the projection must force a **full remaining-balance withdrawal in the deadline year itself** — a second unconditional forced draw, fed alongside (not merged into) the household's `rmd_amount` on its way into `mechanics/plan_year.py::compute_plan_year_mechanics()`. This reuses the mechanism that already exists for the ordinary RMD today: `withdrawal_sequencing.py::compute_withdrawal_plan()` already draws `rmd_amount` unconditionally from the pooled traditional balance *ahead of* the configured withdrawal-strategy ordering; the inherited account's forced draws (annual RMD, and the year-10 full depletion) need the identical "ahead of strategy ordering" treatment, applied to the inherited account's own independently-tracked balance instead of the pooled one.

To key each inherited account's independent balance/deadline state through the projection loop, add `Account.account_id: str | None = None` — a new optional field, auto-generated by `scenario/loader.py` at parse time when omitted (e.g. a stable slug or UUID), the same "optional at parse time, filled in deterministically" treatment `011` gave `owner` for single-member households. A new derived structure — e.g. `inherited_account_state: dict[account_id, InheritedAccountRuntimeState]` — is computed once at resolution time (same seam as `traditional_ownership_shares`) and threaded as a required parameter through `run_plan_projection()`, `KeyError`-eager on a missing entry rather than silently defaulting (again mirroring `011`'s research.md §2 treatment of `traditional_ownership_shares`, itself modeled on `005`'s `survival_curves` precedent).

**Rationale**: The annual-RMD divisor math (§7) and the hard 10-year deadline are two independent IRS rules that happen to interact — a year-10 RMD computed purely from divisor arithmetic could, in principle, be smaller than the account's actual remaining balance, yet the *entire* remaining balance must still come out that year regardless. Folding the deadline into the divisor arithmetic itself (e.g., by trying to make the divisor rule alone produce a full-depletion number in year 10) would silently produce a wrong answer in exactly the years the deadline binds tightest — the two rules need to stay two separate, composable pieces of logic. Reusing the existing "forced draw ahead of strategy ordering" mechanism (rather than inventing a new draw-order concept) keeps this consistent with how the ordinary per-owner RMD already works today. A stable `account_id` is necessary because `Account` currently has no identifier at all — keying inherited-account runtime state by `(owner, account_type, list position)` would be fragile (reordering `scenario.accounts` in a YAML edit would silently reassign state to the wrong account) and would implicitly cap a beneficiary at one inherited account, which has no basis in IRS rules (a beneficiary can inherit IRAs from multiple decedents, each with an independent 10-year clock) or in this codebase's existing "unlimited `Account` entries per scenario" design.

**Alternatives considered**: Encoding the forced full depletion as an ever-growing computed "annual RMD" that happens to equal the remaining balance in year 10 — rejected for the reason above (conflates two independent rules and is wrong whenever the divisor-computed amount and the true remaining balance diverge). Keying inherited-account runtime state by `owner` alone (no new `account_id`) — rejected as an artificial one-inherited-account-per-beneficiary limit with no basis in the underlying rules or the existing schema.

## 9. Explicit out-of-scope / follow-on work

Named here individually, matching `004`'s and `011`'s own practice of stating exactly what a feature does not cover rather than leaving gaps implicit:

1. **Pre-RBD inherited IRA** (owner died before their Required Beginning Date — no annual RMDs required in years 1–9, only full depletion by year 10) — §2.
2. **Spousal rollover election** (a spouse beneficiary treating the inherited IRA as their own, exiting this model entirely and becoming an ordinary `compute_rmd()`-owned account) — §3.
3. **Full EDB stretch computation** for non-spouse EDBs (minor child until age of majority then a 10-year clock starts; disabled/chronically-ill beneficiary; beneficiary <10 years younger) — the taxonomy exists (§3) so this data is capturable, but the divisor/stretch computation itself is not implemented.
4. **Roth inherited IRA rules** — a Roth account's original owner is deemed to have died before their RBD by definition, so no annual RMDs are required during the 10-year window at all, but full depletion by year 10 still applies; this needs its own research pass, not a reuse of §7/§8's traditional-account logic.
5. **Multiple-beneficiary / trust-or-entity beneficiary accounts** — splitting one decedent's IRA among several beneficiaries, each with a separate share and clock.
6. **State-specific inherited-IRA tax treatment.**
7. **The pre-existing, unrelated `RMD_START_AGE` 73→75 step in 2033** (`rmd.py`'s own documented gap) — not addressed by this bead either; remains a separate, already-documented simplification.
8. **Full IRS Pub. 590-B Table I coverage** — ships partial/illustrative coverage first (§7), `verified=False` until cross-checked against a primary source (Constitution Principle III).
9. **UI/BFF surfacing** of the new `InheritedIraDetails`/`account_id` fields (scenario-editing forms, validation-flag rendering for the three new flags in §6) — deferred to the implementation bead.
10. **Mid-simulation death events** (household composition changing during a projection, converting an owned account into an inherited one partway through) — §1.
11. **Monte Carlo simulation support** (`run_simulation()`/`simulation/compare.py`, `005`) — deterministic single-projection and deterministic-comparison support ships with this feature; Monte Carlo requests against a scenario with an inherited account are explicitly rejected, not silently run, until this is threaded through separately (§10 addendum).
12. **Call sites an implementation bead must touch** for the field additions in §4/§6/§7/§8 (listed here so the implementation bead doesn't need to re-derive them): `scenario/models.py` (new dataclasses/fields), `scenario/loader.py:122` (parse `inherited`/`account_id`), `scenario/store.py:63` (serialize the new fields), `scenario/validation.py:36` (the three new flags), `services/bff/src/rp_bff/schemas.py:38` and `services/bff/src/rp_bff/resolution.py:99,114` (exclude inherited accounts from pooling; compute `inherited_account_state`), `mechanics/models.py` (new `InheritedRmdResult`), new `mechanics/inherited_rmd.py` (new module), `mechanics/withdrawal_sequencing.py:59-66` and `mechanics/plan_year.py:72` (thread the inherited account's forced draws alongside the pooled `rmd_amount`), `comparison/projection.py:241` (the per-plan-year loop that currently only calls `compute_rmd()`).

## 10. Addendum (resolved during `/speckit-plan`): integration-level questions Phase 1 design surfaced

§1–§9 fixed every domain-modeling question `rp-2cs` raised; they left a small number of purely mechanical integration questions unanswered because nothing in the bead's own description required them. Phase 1 planning (extracting `data-model.md`/`contracts/` from this research) needed concrete answers to actually wire `compute_inherited_rmd()` (§7) into `run_plan_projection()`. Resolved here rather than reopening §1–§9, since none of these decisions revisit anything already decided above.

**Decision (account type)**: This feature computes distributions for **traditional** inherited accounts only. An inherited account with `account_type` of `"roth"` or `"taxable"` is blocked by a new validation rule, the same way pre-RBD-death and EDB-classified accounts already are (§6) — a fourth rule: `account.inherited is not None and account.account_type != "traditional"`.

**Rationale**: §9.4 already named Roth inherited-account rules (no annual RMD, but the same 10-year depletion deadline) as needing their own research pass — this feature's divisor-and-annual-RMD computation (§7) is specific to traditional accounts and would be wrong if silently applied to a Roth account. A `"taxable"` inherited account isn't a coherent case at all: a decedent's ordinary brokerage account passes to a beneficiary with a stepped-up cost basis and no IRS distribution schedule whatsoever — `InheritedIraDetails` (§4) describes IRA distribution rules that simply don't apply to it. Blocking both, rather than silently computing nothing, keeps this consistent with every other named-and-flagged out-of-scope case in §6/§9 (Principle I).

**Decision (investment growth)**: Each inherited account's own tracked balance (§8, §5) grows using the household's single existing `return_assumption` (the same `ReturnSchedule` — deterministic or per-Monte-Carlo-path — already applied to the household's pooled `AccountBalances` each plan year in `run_plan_projection()`), applied after that year's distribution is subtracted, at the same point in the loop pooled balances are grown.

**Rationale**: This project models one market-return assumption per projection run, not one per account (`004`'s and `005`'s `ReturnSchedule` is a single schedule threaded through the whole household projection) — there is no existing per-account allocation/return concept anywhere in this codebase to attach to an inherited account instead, and inventing one is far outside this feature's scope. Reusing the household's own schedule is the smallest possible extension, and is explicitly documented here as a simplification (Principle I): an inherited account's real-world investments may in fact be allocated differently from the beneficiary's own portfolio, but this feature does not attempt to model that distinction.

**Decision (how a distribution reaches ordinary income and spending)**: An inherited account's distribution for a plan year is real cash the household receives that plan year — it counts toward (a) that year's taxable ordinary income, exactly as the household's own RMD already does, and (b) that year's spending need, ahead of the configured withdrawal-sequencing strategy, exactly as the household's own RMD is already drawn "first, unconditionally" in `compute_withdrawal_plan()` (`003`'s contract). Concretely: `compute_withdrawal_plan()` (`mechanics/withdrawal_sequencing.py`) gains a new parameter `inherited_distribution_amount: float = 0.0`, which reduces `remaining_need` exactly like `rmd_drawn` already does but — unlike `rmd_drawn` — is never subtracted from `starting_balances.traditional` (it was never part of that pooled balance to begin with; the inherited account's own balance is decremented separately, in `run_plan_projection()`, before this call). The returned `WithdrawalPlan` gains a matching new field, `inherited_distribution_drawn: float = 0.0`, both defaulting to reproduce every existing caller's exact current behavior unchanged. `compute_plan_year_mechanics()` (`mechanics/plan_year.py`) gains a matching pass-through parameter and folds `withdrawal_plan.inherited_distribution_drawn` into `ordinary_income_established` alongside `withdrawal_plan.rmd_drawn` and the traditional sequence draws, and folds a new `inherited_rmd_figures_used` parameter into its `figures_used` union alongside `rmd_figures_used` — mirroring that parameter's own existing shape exactly.

**Rationale**: This is the smallest change that makes an inherited distribution behave, for tax and spending-funding purposes, exactly like the household's own RMD already behaves — reusing an established mechanism (`003`'s "RMD drawn first, unconditionally, ahead of strategy ordering" step) rather than inventing a second, parallel draw-order concept. Keeping the inherited balance itself out of `starting_balances`/`ending_balances.traditional` preserves §5's non-pooling decision exactly — only the *amount already distributed* (a plain float, no longer "in" any account) crosses into the pooled-arithmetic function, the same way `rmd_amount` itself is already just a plain float by the time it reaches `compute_withdrawal_plan()`, not a reference to whichever member's account it came from.

**Alternatives considered**: Treating an inherited distribution as pure income with no effect on spending-funding (i.e., it satisfies IRS law and gets taxed, but the household still draws its full configured spending need from its own pooled accounts on top) — rejected: this would double-count the beneficiary's actual cash position (money forcibly received is money the household doesn't also need to withdraw from its own accounts to cover the same spending) and has no basis in how the household's own RMD is already modeled. Making `compute_inherited_rmd()` itself responsible for the withdrawal-sequencing/tax integration (rather than keeping it a pure divisor-arithmetic function like `compute_rmd()`) — rejected for the same contract-separation reason §7 already gives for not folding this logic into `compute_rmd()` itself.

**Decision (`Account.account_id` generation)**: When a scenario's YAML omits `account_id` for a given account, `scenario/loader.py`'s `_build_account()` deterministically assigns `f"{account_type}-{index}"` (the account's own type and its position within `scenario.accounts`) rather than a random UUID.

**Rationale**: `account_id` (§8) exists purely as an internal threading key for one resolved run's per-account state — it is never persisted as meaningful cross-run identity and never enters any numeric computation — so a deterministic, parse-time-computed value keeps `parse_scenario()` a pure function of its YAML input (Principle II: identical input still produces an identical parsed `Scenario`, byte-for-byte, on every run) with no new import (`uuid`) and no hidden randomness anywhere near the engine, unlike a random UUID would introduce.

**Alternatives considered**: A random UUID (e.g. `uuid.uuid4().hex`) — rejected; unnecessary non-determinism for a value with no external meaning, and `parse_scenario()`'s existing 001–011 contract has never depended on any source of randomness.

**Decision (how far `inherited_accounts` threads, and Monte Carlo scope)**: `inherited_accounts` threads through `run_plan_projection()` (`004`) and every function in `comparison/compare.py` (`004`'s deterministic comparisons), each candidate receiving its own independently-copied list since balances mutate in place. It does **not** thread through `run_simulation()` or `simulation/compare.py` (`005`) in this feature — the Monte Carlo path's `_init_worker`/`_run_one_path_shared` multiprocessing boundary (`initargs` passed once to a worker process, reused across that worker's paths) needs its own "fresh copy per path, safe across process boundaries" design, which is a materially different problem from `compare.py`'s simple in-process per-candidate copy. Rather than silently running a Monte Carlo simulation that drops a scenario's inherited-account distributions entirely (a Principle I violation — a confidently-produced but wrong success-rate/percentile number), `services/bff` rejects a simulation or simulated-comparison request against a scenario with any inherited account, with a specific, actionable error, until a follow-on feature threads this parameter through `005` (contracts/bff-api.md).

**Rationale**: This project's own established pattern for "not yet supported" is to reject loudly with a specific message (`scenario.validation`'s blocking flags; `resolution.py`'s `BlockingValidationFlagsError`/`UnknownReferenceValueError`), never to silently produce a plan that quietly omits real, decision-relevant data. A scenario's deterministic single-projection and deterministic-comparison results are complete and correct with this feature; only the Monte Carlo/success-rate path is affected, and rejecting it explicitly there is far cheaper to build correctly than rushing the multiprocessing design in the same pass — matching the same "ship the narrower, well-audited case; name the rest" discipline §2's own RBD-boundary decision already uses.

**Alternatives considered**: Threading `inherited_accounts` through `005` in this same feature — rejected as a substantially larger, higher-risk change (multiprocessing worker state, `_dedupe_figures()`'s figure-union behavior across thousands of paths) that deserves its own focused design pass rather than being absorbed as a late addition here. Silently running Monte Carlo simulations without the inherited account's distributions (i.e., leave `run_simulation()`'s signature untouched and simply never pass `inherited_accounts` to it) — rejected outright as a Principle I violation: the resulting success-rate and percentile-band figures would be wrong, and nothing about the tool's output would tell the user that.
